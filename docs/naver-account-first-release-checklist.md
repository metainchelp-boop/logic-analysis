# 계정 우선 관제 반영 순서

개발 승인 범위만 반영한 후보입니다. 운영 배포·활성화는 별도 승인 후 수행합니다.

## 배포 전

1. AD 초안 PR #12와 BE 초안 PR #828의 최신 커밋·CI 결과를 확인합니다. AD 비교 기준은 운영에 배포된 `abf2406`입니다. 이전 기능 브랜치의 미병합 내역을 생략하거나 덮어쓰지 않습니다.
2. 운영 전체 계정 수·현재 매칭 수·관리부서 직원 수와 수집 스위치를 읽기 전용으로 기록합니다. 기존 원천과 전산 계약별 점검의 수가 다른 것은 오류로 합치지 않습니다.
3. 엔진 중지/재시작 전에 기존 절차로 복구 가능한 일관 DB 백업을 확인합니다. 이번 엔진은 schema 8을 사용하므로 schema 7 엔진 이미지만 되돌리는 방식으로 롤백하면 안 됩니다. DB와 이미지를 같은 기준으로 복구해야 합니다.

## 반영

1. **BE 먼저:** 엔진 키 전용 전체 업체 목록과 조직 자료 `is_management`를 배포합니다. 기존 계약·번호·담당 데이터는 수정하지 않습니다.
2. **전용 경로:** nginx의 정확한 `GET /api/ad-sync/naver-account-catalog` 한 경로를 추가하고 설정 검사 후 기존 승인된 절차로 반영합니다. 다른 메서드·유사 경로·임의 쿼리는 여전히 차단합니다. 전체 목록 응답은 최대 30MiB이며 초과·절단은 전체 실패로 처리합니다.
3. **관제 엔진/UI:** 새 코드로 교체하되 원천 수집 스위치는 처음에는 OFF로 둡니다. 조직 수락본에 재직 관리부서 값이 실제로 들어왔는지 먼저 확인합니다. 필드 누락을 추측값으로 채우지 않습니다.
4. **원천 읽기 활성화:** 별도 승인한 설정에서 `NAVER_ENGINE_INVENTORY_ENABLED=true`로 켭니다. 전체 업체 목록·ID 자료·이관 목록을 수락한 뒤 원장을 대조합니다. 광고 쓰기·자동입찰·보고서 발송 스위치는 켜지 않습니다.

## 운영 검증

- 현재 이관 목록 수 = 전산 매칭 + 전산 업체 미확인 + 미분류 합계인지 확인합니다. 철회/목록 실패/자료 노후화는 정상 매칭·미등록 판정으로 보이지 않아야 합니다.
- 진행중·홀딩중·환불중·환불완료·계약만료 및 나머지 실제 업무 단계 표본을 전산과 대조합니다. 날짜로 임의 상태 전환하지 않습니다.
- 대표는 전체/미매칭을 볼 수 있어야 합니다. 관리직원은 본인 주/부/유효한 직전 담당 계정만 보이고 타인 직접 주소·직원 선택·숨김 업체는 차단돼야 합니다. 관리팀장도 동일합니다.
- 우측 명단에 재직 관리직원과 해당 직원이 볼 수 있는 중복 제거 계정 수만 나오는지 확인합니다. 공동 담당 계정은 두 직원에게 각각 집계될 수 있으므로 직원별 숫자의 합은 전체 수와 다를 수 있습니다.
- 목록 표시/매칭 완료와 원천 지표 수집 완료를 구분합니다. 1,798개를 가정한 첫 수집은 현 예산으로 약 10~15시간에 추가 작업·재시도 시간이 붙을 수 있습니다. 이는 합성 처리량 추정이며 운영 SLA가 아닙니다.
- 원천 상태 `pending/reading/partial/retry/reauth_required/limited/ok` 수를 각각 확인하고, 일부 수집을 전일 합계 0이나 완료로 표시하지 않는지 확인합니다. 회사에 이관됐어도 API 접근 거절이 있으면 별도 사유로 남깁니다.
- 실제 광고 변경·ERP 업체 생성·담당/업무 단계 변경·보고서 발행이 0건인지 확인합니다.

운영 계정 수 대조와 실제 관리직원 로그인은 격리 브라우저 시험으로 대신 완료 처리하지 않습니다.
