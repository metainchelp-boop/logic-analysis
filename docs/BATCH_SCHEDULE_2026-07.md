- **신고**: 직원(윤채은) 07-27 10:12, 로직분석 실행 중 오류.
  화면 토스트 2건 — `서버 오류가 발생했습니다. (502)`, `상세페이지 분석 실패: 요청 실패 (502)`.
  (502는 FE가 서버 응답 상태코드를 그대로 표기한 것 — 임의 문구 아님.)
- **확인 결과 (07-27 10:21~10:25 조사)**
  - 조사 시점 서비스는 **정상**: `/api/health` 10회 연속 200, `/api/seo/detail-page` 401(라우트 정상).
  - **배포 원인 아님**: 마지막 배포는 3일 전(07-24 12:30), 당일 커밋·배포 없음.
  - **유력 원인**: 09:00 「전체 분석 + 보고서」 배치가 *활성 업체 × 키워드*마다 `sleep 1~2초`로
    돌아 **1시간 이상 지속**되는 장시간 작업이고, 10:00 「리포트 발송」까지 겹쳐
    업무시간(10시대)에 부하가 걸림. 이 배치는 사용자 요청과 **같은 컨테이너**
    (RAM 1.9GB · uvicorn 워커 5, `BackgroundScheduler` in-process)에서 실행됨.
    본 저장소엔 과거에도 *워커 메모리 사망 → 502* 전례가 문서화돼 있음(`/api/cd/my-clients` 502).
  - **미확정**: OOM인지 컨테이너 재시작인지는 서버 로그(`docker logs`·재시작 횟수)가 필요.
    `/api/health`에 업타임이 없어 외부에서 판별 불가. → 후속 개선 후보(아래).

## 조치 — 배치 체인 전체를 새벽으로 이동 (운영자 승인 2026-07-27)

의존 순서(계약동기화 → 순위추적 캐시 → 전체분석 → 리포트 발송)를 **유지한 채** 통째로 당김.

| 작업 | 기존 | 변경 | 비고 |
|---|---|---|---|
| 계약단계 동기화 | 07:30 | **04:00** | 분석 전에 만료 업체 제외. ③ 광고센터 06:00과 분리 유지 |
| 순위 추적 | 08:00 | **04:30** | 키워드당 1회 API, 결과 캐시 |
| 전체 분석 + 보고서 | 09:00 | **05:00** | 04:30 캐시 재사용 |
| 일일 리포트 발송 | 10:00 | **08:00** | 업무 시작(09:00) 전 도착 |
| DB 자동 백업 | 00:30 | 00:30 (변경 없음) | |

- **분석 → 발송 여유: 60분 → 180분** (장시간 배치에 대한 헤드룸 3배).
- **업무시간(09~18)에 시작하는 배치: 없음.**
- 파일: `backend/scheduler.py` (cron 4곳 + 모듈 docstring · 시작 로그 · 섹션 주석 시각 표기 정리).

### 검증 (2026-07-27)
- APScheduler `CronTrigger` 드라이런 — 다음 발화 04:00 / 04:30 / 05:00 / 08:00 (KST) 확인.
- 의존 순서 정렬 · 발송 < 09:00 · 06:00 비충돌 · 업무시간 배치 없음 — 전부 assert 통과.
- `py_compile` 통과. 배포 회귀 게이트 8/10 — **실패 2건은 main 기준과 동일**
  (샌드박스 네트워크 차단 탓, 변경 무관. CI에선 통과 이력 있음).

1. **① 메타 전산에 통지** — ad-sync 소비 합의문에 우리 호출 시각이 **07:30**으로 기재돼 있음.
   **04:00으로 변경** 통지 필요(1일 1회·읽기 전용·단계당 1콜·③ 06:00과 분리 조건은 그대로).
   `CLAUDE.md` 경계 원칙 항목도 04:00으로 갱신 완료.
2. **원인 확정 수단 부재** — `/api/health`에 업타임·재시작 카운트 노출 추가 검토.
   같은 신고 재발 시 즉시 OOM/재시작 판별 가능해짐. (미착수, 운영자 결정 대기)
3. **리포트 발송 시각 DB 설정 주의** — `notification_settings.report_time`이 있고 관리자가
   알림 설정을 저장하면 `reschedule_report()`로 **런타임에 발송 시각이 덮어써짐**.

   관리자가 설정 저장 시 DB값(기본 `09:00`)으로 되돌아갈 수 있음 — 인지 필요.
