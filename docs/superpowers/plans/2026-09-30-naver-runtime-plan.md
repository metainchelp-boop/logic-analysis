# 네이버 관제 S14 실행 연결 — 개발 계획

기준: PR #6 `3310059372ddb59772342b4d0607072f952336d4`.
2026-09-30 대표 「응 이어서 진행해」: Q7 권고안 확정. 관제는 SQLite WAL과 단일 쓰기 연결을 사용하고, 실제 광고 자동조정 전에 DB를 다시 검토한다.

## 범위와 경계

- 기존 v1.8 설계의 S14를 이어서 개발한다. 새 광고 기능·광고 쓰기·옛 자동입찰 재가동은 없다.
- 이번 구현 조각: 실행 설정, 단일 쓰기 연결, 예약 점검 연결, 내부 소켓 서버, 백업·복원 도구, 배포 준비 파일.
- 배포·머지·운영 비밀값 등록·운영 API 호출은 하지 않는다. 모든 가동 스위치 기본 꺼짐.
- 실제 가동은 BE #805, 공유 성과 연결(G1~G3), 일회용 코드(S16), 서버 보안·자원·백업 복원 실측까지 별도 게이트로 남긴다. 준비 파일이 있다는 것을 배포 가능 판정으로 쓰지 않는다.

## 구현 순서와 확인 방법

1. 엄격한 설정 읽기 → 기본값으로 DB·통신·키 조회 없이 계획만 확인. 잘못된 스위치·경로·미완성 웹 활성화를 거절한다.
2. SQLite 연결 소유 스레드 하나 → 동시 호출 직렬 처리, 대기 중 취소된 요청이 나중에 저장되지 않는지, 재시작·다중 쓰기 차단 확인.
3. 예약 실행 조립 → 조직·단계 → 연결 목록·짝 → 아침 점검 → 경보·심박의 기존 규칙 호출. 느린 외부 조회 중에도 DB 쓰기 연결은 비워 둔다. 회차마다 새 reader, 실패 간격, 그림자 상태 유지 확인.
4. 유닉스 소켓 서버 → 소켓 폴더 공유·660·신뢰 표지, 제한된 동시 처리, 비밀값 없는 오류, 정상 종료 확인. 웹은 일회용 코드 연결 전 활성화 거절.
5. 백업 → 온라인 일관 사본·압축·공개키 암호화·새 파일만 받는 수신기·영수증·복원 무결성/줄 수 비교. 임시 합성 자료만 사용.
6. 패키징 → 별도 compose 프로젝트, 공개 포트 0, 코드 밖 데이터, 기존 서비스 무접촉, 설정·백업·복원 게이트 문서화.
7. 회귀·독립 검토 → Python 3.12에서 새 시험과 기존 시험 실행. 실제 네이버·전산·서버 검증과 구분하여 결과 기록.

## 구현 판단

- 순수 엔진 `naver_engine/`의 DB·통신 관문 규칙을 유지한다. 운영 실행 조립은 `naver_runtime/`에 분리하고, 외부 연결/프로세스 실행의 허용 지점을 별도 구문 시험으로 고정한다.
- 긴 네트워크 요청을 SQLite 소유 스레드에서 실행하지 않는다. 예약 작업은 제한된 공개 저장소 메서드를 큐로 호출하고, 화면의 한 저장 작업은 기존 `write(fn)`으로 묶는다.
- 배포 전 별도 운영 검증이 필요한 항목은 완료 처리하지 않는다.
