# 공유 네이버 성과 연결 — G1~G3 실행 계획

승인: 대표 「그럼 다음 작업 진행하자」. 기존 설계 G1~G3 적용. 개발·격리 검증만, 머지·배포·운영 조회/쓰기 없음.

## 순서와 완료 기준

1. BE #805 인증 계약과 최신 master #822를 보존한 별도 가지에서 §14 계약을 추가한다.
2. `POST /api/ad-sync/naver-metrics`: 키 먼저 확인, 2KB 이내 엄격 JSON, 가망 번호·정확한 30일 기간·정수 지표만. KST 어제 종료. 엔진 전용 키만.
3. NAVER 자동 행은 API/ENGINE 공동 한 행, client 행 잠금으로 경합 방지. ENGINE 최종 수신 시각 72시간까지 자체 키 조회 생략, 초과 시 복귀. MANUAL은 조회 정리/갱신 대상에서 제외. 복수 active 광고주 매핑은 임의 선택하지 않는다.
4. 관제 29일 비교는 보존하고 공유용 30일 전체 연결 계정·캠페인 확정 자료를 따로 검증한다. 누락·잠정·짝 변경 시 전송 금지, 마지막 값 보존. POST 성공만 완료 기록, 제한된 재시도.
5. 런타임 별도 스위치 기본 OFF. 아침 알림/심박 우선. 기존 광고 API 쓰기·웹 로그인 경로는 변경하지 않는다.
6. 숫자·날짜·인증·수동 보존·fallback·중복/경합·다중 계정·불완전 자료·실패 재시도 시험. 테스트 먼저 실패 확인 후 구현. BE 실제 H2/Spring, 엔진 Linux 외부망 차단 CI.
7. 고정 기반 대비 명세/표준 독립 검토 후 수정, 재검증, 별도 PR. 결과는 구현/시험/운영 미검증을 나눠 기록한다.

## 계약 §14

요청 1건: `possibility_id` (정수 1..10^15-1), `period_start`, `period_end` (YYYY-MM-DD, KST 어제까지 정확히 30일), `impressions`, `clicks`, `spend`, `conversions` (정수 0..9007199254740991). 추가 칸/중복 키/문자 숫자/실수/불리언/후행 JSON 거절.

정상 응답: `{"status":200,"result":{"recorded":true,"reason":"stored"}}`. active 광고주 없음: `recorded:false,reason:"no-client"`. 복수 active 광고주: 409(임의로 첫 광고주를 고르지 않음). 거절/부분 실패는 성공으로 저장하지 않는다.

## 경계

- S16 일회용 로그인, 서버 키·방화벽·자원·실백업 복원, 배포는 후속 단계이다.
- 화면 형태/광고비 공개 범위 유지. source 문구만 실제 수집 출처와 일치시킨다.
- 운영 고객/계정/키를 테스트에 사용하지 않는다. Mac flock/SQLite 제약을 우회하지 않고 Linux에서 DB 시험한다.
