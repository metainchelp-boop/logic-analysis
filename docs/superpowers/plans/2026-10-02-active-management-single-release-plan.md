# 실관리 관제 통합 구현 계획

설계: `docs/superpowers/specs/2026-10-02-active-management-single-release-design.md`.
사용자 업무 선택은 확정됐다. 중간 배포 없이 모든 변경과 통합 검증을 하나의 릴리스로 묶는다. 별도 writing-plans 스킬은 현재 목록에 없으므로 승인 설계에서 직접 검증 가능한 순서로 작성한다.

## 개발 순서와 소유 범위

1. 수집 정책: 일일4단계·일요일 비관리·단계 변경·수동 제외/복귀·권한을 독립 정책으로 만들고 저장/실행에 연결한다. 전체 이관 원장은 유지한다.
2. 일별 자료: 실제 실적일과 시도일 분리, 성공 자료 보존, 제한된 과거 채움, 전환 미확인과0구별. 주간 비관리 최근7일과 매월3일 전월 집계를 지원한다.
3. 보고서: 저장 자료 기반 주간/월간 집계·생성 상태·중복 방지·지연 재개·검토/수정 기록. 기존 다매체 AI 보고서와 분리한다.
4. 원장/관리 화면: ERP관리 업체 누락 대조·구체 매칭 사유·직원 본인 범위 조작·시도와 마지막 정상 자료·주간 비관리 집행 표시.
5. 광고 사유: 네이버 상태/원문 코드와 의미, 상위 계층, 수집 사유를 분리하고 재시작 복원 시 상세를 보존한다.
6. 통합: 실제 Writer/서버/API/중계/브라우저 연결과 SQLite 변경·구버전 자료 보존·배포 복구를 검사한다.
7. 독립 검토와 전체 회귀 후 단일 릴리스. 배포 성공과 실제 원천 자료 완결을 별도 검증한다.

## 실패부터 확인할 핵심 행동

- 같은 이관 목록에서도 진행중은 매일, 환불/홀딩/만료는 일요일에만 자동 후보가 된다.
- 비관리 주간 점검은 완료된7일을 대상으로 하며 일요일 실패 시 월요일에도 상태를 이어 간다. 토/일 자정과 연/월 경계를 한국시간으로 계산한다.
- 단계 변경 동기화 후 기존 수집 주기를 즉시 다시 계산하고, 오래된 단계/권한이나 타 담당 요청은 거절한다.
- 직원은 본인 담당만 확정·포함·제외하고 충돌을 임의 해소하지 못한다.
- 첫 수집 대기와 재시도 중 과거 성공값을 구분한다. 마지막 시도/성공/실적일/잔액시각을 혼용하지 않는다.
- 누락 날짜/캠페인/전환은0이 아니다. 여러 계정과 ROAS의 분모를 일치시키고 보고서 생성 실패는 다음 실행에 재개한다.
- 월요일 보고서는 전주 월~일, 매월3일 보고서는 전월1일~말일이며 월말 마지막 날짜를 빠뜨리지 않는다.
- 수집/매칭/광고 원천 사유가 섞이거나 소실되지 않는다. 알 수 없는 코드는 원문을 남기고 정상으로 판정하지 않는다.
- 반복 수동 요청·재시작·단계 경합·429에서 중복 실행/우회 호출/정상 자료 소실이 없어야 한다.

## 제외와 정직한 완료 기준

- 직원 Chrome 장애, 실제 입찰/광고 변경, 유료 AI 신규 지출, 고급 자동화 안전 설계는 제외한다.
- 제품 예약 기능을 개발하는 작업이며 Codex 개인 알림을 대신 생성하지 않는다.
- 설치·키 재설정·기존 데이터 일괄 초기화·호출 차단 우회는 하지 않는다.
- 코드/합성 시험, 운영 연결, 실제 수집, 실제 직원 사용은 서로 다른 증거다. 미실행 단계를 완료로 표시하지 않는다.
