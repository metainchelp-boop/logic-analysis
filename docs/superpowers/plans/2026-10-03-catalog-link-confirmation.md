# 업체 목록과 연결 확인 기준 통일

승인 근거: `2026-10-03-managed-matching-gaps.md`의 다음 보완 1~3번에 대한 대표의 「다음 진행해」. 운영 연결·전산 번호 변경·배포는 포함하지 않는다.

## 설계 경계

- 검증 모드의 연결 목록과 확정만 현재 수락된 catalog 및 전체 계정·번호 주장·사람 판단으로 계산한다. `inventory._matching`의 동일 규칙을 재사용한다.
- 기존 `views.Ctx`와 prospects를 전역 확장하거나 합성 행을 삽입하지 않는다. 아침 점검·보고서 자격은 바꾸지 않는다.
- catalog가 한 번도 없었던 설치만 기존 경로를 유지한다. catalog 실패·만료는 기존 목록으로 우회하지 않는다.
- 전체 자료로 충돌을 판단한 후 담당 범위로 노출을 제한한다. 대표/본인 담당 권한, 이름 후보·번호 충돌 차단을 유지한다.
- opaque ref는 원천 내용·시각·조직·담당 범위·판단 이력·연결쌍·사유를 결합한다. 같은 시각의 내용 교체도 옛 ref를 무효화한다.
- 저장 큐에서 최신 신원/원천을 다시 확인하고 실제 거래 안에서 원천 일치 여부를 재검사한다. 이름이 다르면 단건 원본 광고 계정 ID 대조를 요구한다.
- catalog-only 업체의 상세 경로를 기존 prospects 상세로 잘못 열지 않는다. 대상 업체 필터·빈 결과 안내·원천 오류 안내를 제공한다.
- 50개 단위 확인 뒤에는 새 ref를 받아야 한다. 처음 선택한 연결쌍만 이어 처리하며 조회 중 추가된 업체를 포함하지 않는다.

## 구현·검증 순서

1. 공개 WSGI의 catalog-only 누락을 실패 시험으로 고정한다.
2. 연결 전용 모듈과 검증 모드 경로를 구현한다.
3. 단건 확인, 담당 권한, 원천 변경/만료, 충돌, 거래 직전 경합을 순차 시험한다.
4. 업체별 이동 및 필터 범위 확인을 DOM/API 계약과 합성 브라우저에서 검증한다.
5. 기존 회귀 + Linux 전체 CI를 확인하고 개발 브랜치에만 반영한다.

검증 구분: 합성 SQL/HTTP/브라우저와 운영 연결·배포 결과를 혼동하지 않는다. 기존 운영 11곳이 자동 연결됐다고 보고하지 않는다.
