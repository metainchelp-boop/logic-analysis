첨부 다운로드 CSV는 해당 경로에 없었다. 보존된 붙여넣기 원본에는 광고 계정 ID1,779개가 있고 중복·숫자 형식 오류는 없었다. 전산 업체 식별번호 대응열은 없다. 현재1,793 목록과 과거1,779 목록의 단순 차이를 이관 누락 수로 간주하지 않는다.

이름 불일치11곳 모두 원본의 고객사명은 전산 상호명과 공백 제외 정확 일치하는1행이 있었고, 계정 이름은 별칭이었다. 그11개 번호와 별도 충돌1개 번호 모두 현재 이관 계정 표에 존재했다. 그러나 전산에 현재 저장된 명시 번호와 원본 번호의 동일 연결쌍·충돌·현재 담당 권한까지 검증하여 확정한 것은 아니다. 이름만으로 연결하지 않는다. 업체별 대조표는 개인정보 최소화를 위해 원격 저장소가 아닌 로컬 `outputs/naver-matching-name-mismatch-20261003.md`에 보관했다.

## 연결 확인 경로 결함 — 재현 완료, 미수정

실제 화면에서 이관 현황의 이름 불일치 업체의 「짝 확인 열기」를 눌렀으나 해당11업체가 열린 확인 목록에는 없었다. 아래 합성 재현은 코드의 누락 경로를 입증하며, 운영11곳 모두 같은 내부 원인이라고 단정하지 않는다.

1. 실제 Store·메모리 SQLite, 현재 조직·계정 목록·catalog 안에 합성 업체를 넣고, 별도 prospects에는 그 업체가 없게 한다.
2. 같은 대표/본인담당 권한으로 `inventory.board`는 업체를 미연결/name-different로 내보내지만, 실제 `links.pair_links` → `views.links_pending` → `GET /links/pending`에는 업체가 없다. 후보0과 후보1 모두 같은 누락이다.
3. 조직·계정·확인 권한은 바꾸지 않고 prospects 소속만 추가하면 해당 행이 나오고 검증 모드에서도 확인 가능하다. 타 담당자는 추가 전후 모두 숨김을 유지한다.

원인 경계: 이관 현황은 catalog 전체를 분모로 삼고, 기존 짝 확인은 prospects와 저장 pairing을 사용한다. 화면의 확인 버튼 필터보다 앞에서 누락된다. 관련 코드는 `inventory.py::_managed_coverage/board`, `links.py::pair_links`, `views.py::load/visible/links_pending`, `web.py::_verified_row_allowed`이다.

로컬 재현 `outputs/diagnostics/test_managed_coverage_links_gap.py`:5개 중 기대 동작2개가 `11 not found in set()`으로 실패, 같은 권한의 소속 변경·타 담당 차단·공개 WSGI 대조3개 통과. 기본 CI 밖의 **미해결 결함 재현 자료**이며 제품이나 통과 시험으로 올리지 않았다.

## 다음 보완 순서

1. 현재 catalog 기준의 계정 확인 목록과 확정 요청 검증을 한 원천으로 맞춘다. 단순히 옛 prospects 표에 합성 업체를 넣거나 기존 권한 검사를 제거하지 않는다.
2. 조회 시 연결쌍과 확정 시 연결쌍·원천 시각을 묶고, 새 원천/다른 담당/번호 충돌이면 재확인하도록 시험한다. 대표·본인담당·타담당·원천 만료·경합을 포함한다.
3. 이관 현황의 해당 업체에서 그 업체의 확인 항목으로 직접 이동한다. 대상이 없으면 없다고 설명하고 빈 목록으로 유도하지 않는다.
4. 원본 대조 가능11곳부터 현재 저장 번호와 연결쌍을 검증한다. 충돌1곳은 대표 판단 대상으로 남긴다. 후보117/복수19/근거 없음330도 번호 근거가 확보된 것만 연결한다.
