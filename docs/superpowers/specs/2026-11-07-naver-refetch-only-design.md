# NAVER 과거 암호문 전체 재회수

대표가 전체 다시 받기를 선택했다. 이번 변경은 개발·시험·PR 준비까지이며, 서버 B 설치와 실행은 PR 검토 후 대표 승인 단계다. 기존 원본 정리와 복구 키 이동은 포함하지 않는다.

## 문제와 선택

기존 회수는 3,600초 제한에 도달해 전체 암호문의 59.5%만 Mac에 남았다. B의 완성 암호문은 원래 전송 영수증과 전량 SHA-256·길이가 일치했다. Mac 부분 파일도 같은 암호문의 앞부분과 일치했지만, 복호화 검증은 시작하지 않았다. 기존 임시 접근은 정확한 설치 영수증으로 철회했다.

전체 재회수는 기존 전송 검증과 복구 형식을 유지한다. 이어받기는 prefix/offset/tail 프로토콜이 필요하므로 이번 범위에서 제외한다. 기존 부분 파일을 읽기 전용으로 보존하고 새 이름에 전체 암호문을 받는다.

## 고정 범위와 증거

- 데이터 세션과 B 암호문 경로는 기존 `naver-archives-20261106-v1/archives.gpg` 한 개다. B 데이터 파일·기존 도구·VPS는 변경하지 않는다.
- 새 인증 범위는 `naver-archives-refetch-20261107-v1`. 새 전용 폴더에 receiver, 해시가 고정된 기존 파일 검사 코드, closed config를 배타 설치한다. 새 파일은 0600, 폴더는 0700이다.
- 원래 plan/sent/기존 install/revoke의 원문 SHA와 폐쇄형 형식을 대조한다. 같은 회수 공개키 하나와 Mac IPv4 하나만 허용한다. 개인 키 본문은 읽거나 복사하지 않는다.
- B는 기존 secondary 인증의 부재와 primary 동일성, 기존 잠금 파일, 완성 암호문의 안전한 경로·소유·권한·링크 수·identity·전체 길이와 SHA를 확인한 후에만 새 인증을 게시한다. 새 config에 원래 증거와 실제 cipher identity를 결속한다.
- 새 forced command는 전체 fetch 하나만 허용한다. receive, 임의 경로, offset, 인수와 명령은 거부한다. 기존 install 가드 우회나 이전 만료 문자열 수정은 없다.

## 시간 예산

실제 암호문 3,256,576,677바이트를 300,000바이트/초(0.3MB/s, 십진)로 나누면 10,855.256초, 약 181분이다. 앞선 2시간 후보는 전체 재회수에 부족하다.

| 경계 | 고정 상한 | 포함 범위 |
| --- | ---: | --- |
| B 설치 | 480초 | 입력·파일 전량 검증과 인증 게시 |
| Mac 설치 교환 | 600초 | SSH 연결, B 처리와 영수증 수신 |
| B fetch | 14,400초 | config/전량 검증, 송신, 종료 |
| Mac fetch | 16,200초 | 준비, 부분 파일 보존 대조, 연결, 수신, 전량 재읽기, 게시와 결과 기록 |
| 새 인증 | 21,600초 | 발급부터 6시간 |
| 새 회수 시작 | 발급 후 1,800초 이내 | Mac과 B에서 각각 검사 |

B 송신 예산에는 0.3MB/s 전송 계산보다 약 59분의 여유가 있다. 시작 마감 30분과 Mac 4시간 30분을 합쳐도 인증 창에 1시간이 남는다. 더 낮은 속도나 단절에서는 다시 실패할 수 있으며 시간마다 예산을 초기화하지 않는다. 자동 재시도·연장은 없다.

## 회수와 실패 처리

B는 기존 데이터 잠금에 참여하며 암호문을 읽기 전용으로 연다. 고정된 config/identity와 전체 SHA를 대조한 뒤 처음부터 정확한 길이만 전송한다. 전송 중과 종료 시 파일 불변 및 전송 SHA를 대조한다. stdout은 암호문 바이트만 사용하며 성공은 종료 0을 요구한다.

Mac은 원래 입력 영수증과 새 설치 영수증의 결속을 확인한다. 기존 `archives.gpg.partial`은 안전한 읽기 전용 fd에서 전체 SHA와 identity를 확인하고, 새 `archives-refetch-20261107-v1.gpg` 및 그 partial은 배타 생성한다. 기존 `stream_fetch`의 SSH 종료·EOF·길이·SHA·전체 재읽기·배타 게시 검증을 재사용한다. 기존 부분 파일은 성공/실패 후에도 삭제하거나 이름을 바꾸지 않는다.

수신 성공은 `fetched_unverified`다. 원래 plan/sent와 새 완성 암호문을 기존 recover에 입력해 전용 보안 입력창에서 복호화하고 내부 파일·원본 SHA·격리 복원을 검증해야 한다. 이번 PR이 이 검증 성공이나 원본 삭제를 대신하지 않는다.

실패 시 새 partial/final/결과 영수증과 기존 partial을 남긴다. 성공으로 추정하거나 자동 재실행하지 않는다. 실행 종료를 확인한 뒤 새 설치 영수증과 정확히 일치하는 secondary 인증만 철회하고 primary 불변을 확인한다. 만료와 철회는 활성 프로세스 종료 증거를 대신하지 않는다.

## 구현과 검증 순서

1. 새 B 전용 receiver/controller와 합성 파일·명령·만료·잠금·게시 실패 시험.
2. Mac 설치/철회 operator와 입력·키 메타데이터·SSH 옵션·응답 유실·영수증 결속 시험.
3. Mac 전체 회수 wrapper와 실제 합성 subprocess를 통한 시간 초과·잘린 스트림·잘못된 SHA·nonzero 종료·기존 partial 보존 시험.
4. 관련 회귀, 독립 검토, 비밀정보 검사, GitHub PR와 정확한 최종 커밋의 Linux CI.
5. 검토 뒤 운영 승인 시에만 별도 새 도구 설치 → 새 인증 → 새 경로 회수 → 기존 recover → 정확 철회. VPS 원본 정리는 복구 영수증 확인 후 담당자가 진행한다.
