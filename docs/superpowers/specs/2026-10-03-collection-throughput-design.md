# 수집 처리량과 실패 원인 보존 개선

상태: 대표 승인 방향의 구현·검증 계획. 운영 배포와 실계정 성능 검증은 별도이다.

## 목적과 범위

출근 시 전일 자료 확인을 위해 내부 중복 호출과 불필요한 대기를 줄인다. 운영 중인 847be08의 읽기 전용 권한, 원천 세대 검증, 담당 범위, 원장 보존, 네이버 제한 대응은 유지한다. 광고 변경·입찰·자동화 활성화·운영 설정 변경은 포함하지 않는다.

## 확인된 원인

- 전일도 캠페인마다 통계 한 번씩 읽는다. 캠페인 N개는 목록·잔액·최종 목록을 포함하여 N+3회이다. 6개면 9회인데 계정별 회차 상한은 8회라 정상 응답만 받아도 다음 회차로 넘어간다.
- 한 회차 종료 뒤 항상 60초를 기다리고 예약기에서도 60초를 제한한다. 요청은 초당 3회, 회차는 24회/30초 이내인데 남은 시간과 무관하게 추가 대기한다.
- 파싱·지표·기준 시각 오류가 STATS_INCOMPLETE로 합쳐지고 재시도 소진 시 RETRY_EXHAUSTED로 덮여 원인이 사라진다. 운영의 해당 건들을 실제 네이버 미수신으로 단정할 근거는 없다.

## 구현 계약

1. 단일 닫힌 날짜만 기존 GET /stats의 복수 캠페인 합계를 이용한다. 최대 100개씩, 캠페인별 값과 원천 시각을 확인하고 기존 체크포인트 형태로 저장한다. 누락된 캠페인만 일별 응답으로 확인한다. 누락·미확인 지표를 0으로 채우지 않는다. 여러 날짜의 기간 합계를 날짜별로 나누지 않는다.
2. 파서 오류는 허용 목록의 `StatsShapeUnknown.code`로 보존한다. 단일 원천 지표 누락·숫자 오류·날짜 오류·기준 시각 오류를 분리한다. 원문, 키, 업체 정보는 코드에 넣지 않는다. 수집기 자체의 오류도 같은 방식으로 전달한다.
3. 저장소는 재시도 소진 상태를 `limited`와 횟수로 나타내고 마지막 실제 `error_code`는 보존한다. 기존 스키마 11을 유지한다. UI에는 정해진 한국어 설명만 표시한다.
4. 수집 회차는 단일 실행기에서 최소 30초 간격으로 예약한다. 실제 호출한 회차 완료 후에도 30초 안전 간격을 두어 이전 회차 후반과 다음 회차 초반의 호출이 한 30초 창에 몰리지 않게 한다. 전체 작업 종료 뒤 무조건 60초를 추가로 쉬는 대신 다음 작업 예정까지 기다린다. 24회·30초 회차 예산, 성과 18회·20초, 구조 최대 6회, 계정 8회·10초, 초당 3회는 그대로이다. 비수집 작업은 기존 주기를 유지한다. 429 발생 시 다음 새 reader에서도 최소 기존 5분 제한을 존중하며 중첩 실행하지 않는다. 운영 배포 전 보수적 예산은 올리지 않는다.

## 검증과 완료 기준

- 각 변경은 실패하는 회귀 시험을 먼저 추가하고 통과시킨다.
- 같은 실제 수집기 코드에 무통신 가짜 전송기·시계를 연결해 1/6/25개 캠페인에서 호출 수, 한 회차 완료 계정 수, 예산·대기를 비교한다. 합계 일치와 누락 0 처리 금지를 같이 검증한다.
- 부분 응답, 전환 미확인, 오래되거나 미래인 원천, 세대 변경, 재시도 소진, 429, 느린 응답, 재시작 이어읽기, 여러 날짜 수집 회귀를 검사한다.
- 기존 엔진·실행기·화면 테스트를 실행하고 실계정 운영 결과와 가상 측정을 구별한다. 전체 계정 완료 시각은 운영 실측 전 보장하지 않는다.

## 분업과 순서

1. 파서 진단 코드, 저장소/화면 원인 보존, 예약 대기를 독립 파일에서 병렬 구현한다.
2. 단일 날짜 묶음 조회를 구현하고 인터페이스를 통합한다.
3. 실제 코드 기반 비교 측정, 전체 회귀, 보안·경계 검토 후 변경을 후보 브랜치에 묶는다.
4. 배포는 최종 검증 결과와 함께 별도로 다룬다. 운영 배포를 하지 않은 상태를 완료된 실사용 개선이라고 보고하지 않는다.
