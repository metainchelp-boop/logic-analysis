# 에이전시 광고 계정 ID 기준 관제 매칭

## 승인된 범위

2026-10-01 사용자 승인: 전산 광고주 관리의 계정 정보를 기준으로 광고 계정 ID로 매칭한다. 관제는 이미 보유한 에이전시 자격으로 계정 목록과 성과를 읽고, Customer ID는 내부에서 찾는다. 개별 광고주의 API 키와 Customer ID를 관제 사용 조건으로 요구하지 않는다.

직원 입력 기준은 전산이다. 사전 조사에서 받는 기존 API 3종과 개별 자격 기반 기능은 변경하지 않는다. 이번 작업은 코드와 검증까지이며 운영 배포·DB 변경·실제 매칭 저장은 별도 승인 단계다. 제공된 실데이터는 소스·테스트·공개 로그에 넣지 않는다.

## 계약과 처리

- 전산 업체×매체 계정 정보에 명시적으로 네이버용인 `naverAdAccountNo` 문자열을 추가한다. 기존 `accountId`(로그인 ID) 및 `apiCustomerId` 의미를 바꾸지 않는다.
- `null`/필드 생략은 기존 값 유지, 빈 문자열은 해당 연결번호 해제다. 양의 ASCII 정수(선행 0 없음, 최대 15자리)만 받는다. 기존 API 키·비밀키·로그인 정보는 보존한다.
- 기존 읽기 전용 `/api/ad-sync/naver-customer-ids` 응답에 선택 필드 `ad_account_no`를 추가한다. 기존 `customer_id` 응답과 기존 Customer ID 매칭을 유지한다. 활성 매체·숨김 업체 제외 조건도 유지한다.
- 명시적인 `naverAdAccountNo`가 있으면 `integration_vendor` 미설정이어도 관제 매칭 대상으로 내보낸다. 다른 명시적 연동 종류에 네이버 번호를 새로 등록하는 것은 거부한다. 전역 매체 설정은 변경하지 않는다.
- 에이전시 전체 목록의 `adAccountNo`로 계정을 찾아 내부 `customerId`로 정규화한 뒤 기존 중복 주장·업체명 불일치·사람 확인/거절 보호 규칙을 적용한다.
- 같은 전산 행의 광고 계정 ID와 기존 Customer ID가 서로 다른 네이버 계정을 가리키면 보류한다. 두 번호가 같은 계정이면 한 번만 연결한다. 번호 종류를 숫자 모양으로 추측하지 않는다.
- 목록이 불완전하거나 대응 번호가 중복이면 매칭을 거부한다. 에이전시 목록 접근과 개별 캠페인·성과 접근 성공은 별개로 표시한다.
- 사용자에게 노출되는 입력은 기존 전산 계정 정보 화면의 별도 네이버 관제용 광고 계정 ID 항목이다. 기존 API 3종 입력을 덮어쓰거나 필수화하지 않는다.
- 유효한 전체 계정 목록이 있는 동안 전산 번호는 기존 재시도 제한과 같은 30분 간격으로 다시 읽는다. 네이버 전체 목록의 기존 일일 갱신 주기는 바꾸지 않는다. 계정 번호만으로 연결된 업체의 목록 이탈/복구도 기존 고객번호 기준 이력으로 추적한다.

## 구현 순서와 검증

1. 전산 저장·응답·읽기 조회: 필드 미전송 보존, 해제, 잘못된 숫자 거부, 연동 종류 미설정에서도 광고 계정 ID 조회, 숨김·비활성 제외 및 비밀정보 미포함 검증.
2. 관제 정규화: 명시적인 광고 계정 번호 매칭, 다른 계정의 Customer ID와 숫자가 같은 경우, 동일/상충하는 두 식별자, 전산 업체 간 충돌, 기존 사람 결정 보존 검증.
3. 전산 입력 UI: 저장·재열람, 고객번호와 로그인 ID 구분, 광고 계정 ID 단독 등록과 기존 API 정보 보존 검증.
4. 통합 회귀: 기존 고객번호 응답 호환, 전체 목록 완전성, 계정 이탈 시 기존 보류 상태 유지, 기존 관련 테스트 및 빌드 실행.

## 제외

이름만으로 1,779개 계정을 전산 업체에 일괄 확정하지 않는다. 구 광고센터 DB/키를 관제로 복사하지 않는다. 자동입찰·광고 변경·알림·다른 기능의 자격 입력 폐지는 포함하지 않는다.
