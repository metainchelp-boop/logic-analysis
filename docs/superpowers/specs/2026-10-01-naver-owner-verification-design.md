# 대표 전용 네이버 관제 검증판 — 제한 배포 설계

상태: 대표 전용·업무 쓰기/자동입찰 차단·안전검사 뒤 제한 배포 방향은 승인됨.
10/1 후속 「https 없이는 안돼?」 → 「해결해」: 기존 전산 HTTP는 유지하고 새 관제만
전용 SSH 암호화 전송으로 연결하는 방향 및 백업 전용 실행 경로 보완이 승인됨.
이 문서는 구체 배포 경로와 새로 드러난 인프라 제약을 정리한 검토본이다.
앱 구현·배포 완료를 뜻하지 않는다. 기존 시안을 실제 앱으로 소개하지 않는다.

## 선택지와 권고

1. **권고: 실제 관제 앱의 대표 전용 읽기 검증판.** 기존 광고센터 HTTPS 호스트의
   `/naver/` 경로와 전산 로그인 연결을 사용한다. 실제 자료를 읽어 별도 엔진 저장소에
   보관하며 업무자료 수정은 차단한다. 인증·서버 보안·백업 선행 작업이 필요하다.
2. **대안: 격리된 합성자료로 실제 UI 확인.** `test_screen.py`의 실제 UI/중계/엔진 경로를
   로컬에서 검증한다. 운영자료·실제 로그인 확인은 아니며 시험 서버를 공개하지 않는다.
3. **보류: 정식 관제 전체 배포 뒤 열람.** 연결 범위는 넓지만 함께 보며 확인하려는
   대표 요청에 늦는다. 모든 PR을 일괄 머지하는 것으로 대체하지 않는다.

## 화면과 접근

- 기존 전산에서 대표에게만 네이버 관제 검증판 입구를 표시한다. 기존 광고센터·로직
  입구는 유지한다. FE #1001 전체 전환과 분리한 최소 후보로 검토한다.
- 최종 경로 후보는 `https://dashboard.metainc.co.kr/naver/`이다. 현재 사용 가능한 링크라고
  안내하지 않는다. URL만 열면 로그인되는 구조가 아니라 S16 전산 입구의 창 연결이 필요하다.
- 로그인과 매 요청에서 검증된 직원 번호 및 현재 수락된 조직표의 재직·대표 권한을
  확인한다. 대표 번호 0을 빈 값으로 취급하지 않는다. 대표 권한이 사라지면 다음 요청부터
  거절한다. 조직 정보가 없거나 검증할 수 없으면 열지 않는다.
- 검증판 표시, 자료 기준 시각, 미수집·미점검 상태를 항상 구분한다. 미확인 수치를
  정상 0으로 채우거나 합성자료를 실제 성과로 보여 주지 않는다.

## 업무 쓰기 차단

- 서버에서 조회 GET과 정상 로그인·세션 갱신만 허용한다. 새 업무 변경 경로는 기본 거절한다.
- 이슈 확인/해결/예외, 연결 확인/거절/철회/미리보기, 알림 읽음/전체 읽음,
  기준값 저장, 보류 조직/단계/계정 수락은 차단한다. 화면 버튼 숨김만으로 대신하지 않는다.
- 자동입찰, 공유성과 전산 전송, 업무 알림·심박 전송은 끈다. 기존 자동화 프로세스에
  쓰기 자격을 전달하지 않는다.
- 단회 로그인 코드 소비, 보안 감사기록, 별도 엔진의 읽기 자료 저장은 필수 기술 쓰기다.
  전산·네이버 업무 원장 변경과 구분하며 '모든 디스크 쓰기 0'이라고 표현하지 않는다.

## 자료와 배포 순서

1. 대표 제한/쓰기 차단의 거절 시험과 합성 실제 UI 검증.
2. BE 선행 코드·스키마 충돌·지문 지속 주입 및 안전한 통신 경로 확인.
3. 백업 수신·실제 수신본 회수·격리 복원, 이미지/권한/WAL/단일 쓰기/소켓 검증.
4. 기존 서버의 분리 엔진 프로젝트와 광고센터 중계 준비. 운영 nginx 전체 덮어쓰기,
   기존 DB/볼륨 연결, 임의 공개 포트 추가는 하지 않는다. 기존 앱 기준선과 자원 여유를 대조한다.
5. 조직·계약·고객 연결·아침 점검의 읽기만 연결한다. 계정 목록은 06:30 이후,
   아침 점검은 06:30~08:00의 기존 제한을 유지한다. 시각을 속이거나 제한을 우회하지 않는다.
6. 실제 S16 로그인·권한 거절·민감정보 로그 미노출을 확인하고 대표 입구를 마지막에 반영한다.

운영자료를 연결하는 경우 '검증판'이라는 이름으로 기존 생산 안전 게이트를 건너뛰지 않는다.
공유성과 G1~G3는 비활성 유지하되 기존 생산 배포의 검증 요구 자체를 면제하지 않는다.
14일 관찰 및 실제 자동입찰 활성화는 이번 제한 배포 완료와 별개다.

## 새로 확인된 제약과 결정 경계

- `naver_engine/erp_read.py:37`은 HTTP를 사용하며 기존 설계에는 9/22의 HTTPS 미전환
  결정이 기록돼 있다. S16 수신부는 HTTPS를 전제로 하므로 양쪽을 함께 켜기 전에 통신
  정책을 정합해야 한다. 신규 전용키를 HTTP로 보내거나 인증서 검사를 끄는 대체는 하지 않는다.
- 10/1 이번 로컬 무자격 조회에서 `api.metainc.co.kr:443` 연결은 거절됐다(curl 종료 7,
  HTTP 응답 없음). TLS 협상에 도달하지 않았으므로 인증서 정상 판정이 아니다.
  실제 광고 서버에서의 경로와 기존 서버 설정은 별도 확인해야 한다.
- 기존 전산 전체 HTTPS 전환은 하지 않는다. 새 관제용 SSH 암호화 경로의 로컬
  전송 어댑터를 구현하되 HTTP 직접 접속·DNS/TCP 대체·프록시·리다이렉트로 빠지지 않는다.
  논리 URL 검사는 유지하며 물리 연결만 전용 Unix 소켓으로 제한한다. 네이버 API는 기존 HTTPS다.
- 전용 연결 후보는 별도 SSH 계정/키 → BE loopback 전용 입구 → 기존 blue-green
  upstream이다. 백업 계정의 전달 차단을 풀거나 기존 port80 전체를 전달하지 않는다.
  계약·조직·고객번호 GET 3개와 NAVER_CONTROL SSO 교환만 허용하고 다른 경로/메서드는 거절한다.
- 운영 읽기 진단36794839703에서 자격 없이 정직한 Python UA를 보낸 loopback 계약조회는
  기존 BotBlock 403이었다. 전역 신뢰 IP 추가·UA 위장·보호정책 우회는 하지 않았다.
  지정 4개 API의 전용 인증키 검증 연동 예외는 별도 승인 질문 중이며, 답 전에는 활성화하지 않는다.
- 백업 전용 실행 경로는 BE36794571759에서 적용했다. 기존 Python root:root0700은
  유지하고 사본만 root:백업그룹0750으로 설치했다. SSH 강제명령 두 곳만 변경하고
  관리 SSH 정책·앱 기준선 불변을 확인했다. 합성 전송36794767117은 성공했으며
  실제 수신본 회수36795133908 및 격리 복원36795230254까지 성공했다. 합성 자료이며
  실제 엔진 호스트 발신·운영자료 복원·정기 백업 운영은 별도 검증 대상이다.

## 완료 판정과 중지 조건

- 대표 실제 로그인 성공, 일반 직원/퇴사자/권한 변경/직접 API/변조 요청 거절.
- 모든 업무 POST 거절, 읽기 경로에서 외부 업무 쓰기 0, 자료 기준 시각·누락 표시 확인.
- 기존 전산/로직/광고센터 핵심 흐름 무회귀. 새 엔진만 꺼서 복구 가능한 절차 확인.
- 검증되지 않은 암호화 경로, 원문 자격 로그, 백업 미완료, 원장 쓰기, 조직 권한 불명확 시 제한 배포 중지.
- 연결 준비와 화면 시안, 합성 시험과 실사용, 제한 검증판과 정식 운영을 각각 기록한다.

## 자체 검토

기존 입구/DB 보존, 대표 0번 처리, 기술 쓰기와 업무 쓰기 구분, 시험 서버 공개 금지,
예약 시간 유지, 미수집 표시, 기존 안전 게이트 보존을 확인했다. 승인된 백업 변경과
신규 전송 어댑터 개발을 관제의 실서비스 연결·배포 성공과 구분한다. 보안 정책은 별도 확인 대기다.
