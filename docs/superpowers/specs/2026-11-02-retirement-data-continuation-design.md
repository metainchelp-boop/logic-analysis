# 일시 정지 상태를 유지한 자료 보존 이어가기

## 확인된 상태와 범위

원래 전송 실행 `41412005422`는 두 앱이 일시 정지(`paused`)된 상태에서 실패했습니다. 서버 B의 147바이트 암호문은 검증된 백업이 아닙니다. 이 암호문과 원래 세션의 시도·실패·정리 기록은 그대로 보존합니다. 기존 세션을 덮어쓰거나 재시도 가능 상태로 되돌리지 않습니다.

공개 진단 실행 `41414547844`는 앞선 단계를 통과한 뒤 `stage=configuration`, `error=command_failed`를 반환했습니다. Docker 설정 조회 템플릿의 누락 필드 실패는 로컬에서 재현했지만, 운영에서 어떤 필드가 실패했는지는 아직 확인하지 못했습니다. 수정본의 진단과 실제 보존·복구 검증이 끝나기 전에는 해결 또는 백업 완료로 판정하지 않습니다.

이 작업은 이미 동결된 자료의 암호화 보존을 이어가는 작업입니다. 앱 재개·재기동·종료·삭제와 ERP 활성화는 실행하지 않습니다. 컨테이너·볼륨·원래 파일을 보존합니다.

## 두 세션의 역할

| 역할 | 고정 세션 | 처리 |
| --- | --- | --- |
| 원래 시도 및 복구 자료의 논리 세션 | `data-snapshot-20261102-v1` | 기존 암호문·기록 불변. archive manifest와 원래 restart 정책의 세션도 유지 |
| 새 운송 세션 | `data-snapshot-continuation-20261102-v1` | 별도 운송 키·시도·수신 폴더·영수증을 한 번만 생성 |

새 수신기의 명령은 `receive-data-snapshot-continuation-20261102-v1`로 고정합니다. 새 폴더의 `data.gpg.partial`을 재해시·동기화한 뒤 `data.gpg.pending`으로 게시하며, 기존 partial 또는 pending이 있으면 실패합니다. 원래 세션을 대체 경로로 사용하지 않습니다.

## 소스의 실행 전 조건

- 원래 실패 영수증의 고정 SHA256·410바이트·정확한 필드와 원래 시도 실행 번호를 대조합니다. 완료된 운송 키 정리 기록, 원래 키 쌍 부재, 성공 전송 기록 부재도 확인합니다.
- 고정 Docker CLI 설정 폴더는 관리자 전용이며 비어 있어야 합니다. 원래 기록은 읽기만 수행합니다.
- `prepare`와 `send`는 고정 통제 기록 SHA256을 요구합니다. 컨테이너 ID·PID, 두 앱의 paused 상태, restart 정책 `no/0`, 보호된 nginx 설정을 대조합니다.
- archive의 `Snapshot.frozen()` → 원래 restart 정책 확인 → `Snapshot.frozen()`을 수행합니다. 준비 단계에서는 파일 본문을 수집하는 전체 snapshot 진입이나 archive 생성을 하지 않습니다.
- 이 조건들을 새 세션·키 생성 전에 확인하며, 준비 완료 직전 및 전송 전후에도 필요한 동결·통제 조건을 다시 확인합니다. 새 전송 시도 기록과 암호화 파이프라인은 조건 통과 뒤에만 생성합니다.
- 공개 helper 세 개는 고정 해시의 동일 바이트를 메모리에서 읽어 실행합니다. archive 수정본이 검토·시험·진단을 통과하기 전까지 archive 해시는 모두 0인 값으로 두어 실행을 차단합니다. 해시를 채웠다는 사실만으로 운영 오류 해결이나 복구 성공을 주장하지 않습니다.

소스에는 Docker `pause`, `unpause`, `stop` 실행 경로가 없습니다. 실패해도 원본 앱의 일시 정지 상태를 바꾸지 않습니다. 전역 전송 잠금과 원래 워크플로와 공유하는 동시 실행 그룹으로 겹치는 실행을 제한합니다.

## 전송과 출력 계약

평문 archive는 파이프로만 GPG와 SSH에 전달합니다. 원래 키·환경·고객 본문과 예외 원문을 표준 출력·로그에 싣지 않습니다. 생산자 실패는 검토된 정적 오류 이름만 `producer_` 접두사와 함께 반환합니다.

출력은 `RETIREMENT_DATA_CONTINUATION=` 접두사와 기존의 닫힌 15필드 JSON입니다. `prepare` 성공은 두 앱의 `paused` 및 통제 SHA 일치를 요구하고, `send` 성공은 archive/GPG/SSH의 실제 종료 코드가 모두 0인 `transferred_unverified`만 허용합니다. 실패의 `process_rc`는 null 또는 정확한 세 키이며, 생성·회수되지 않은 자식의 값은 null입니다. 정수 종료 코드는 -255부터 255까지이며 boolean은 거부합니다.

`cleanup`은 완료된 시도와 서버 B 인증 폐기 뒤 운송 키만 제거합니다. 출력 paused 값은 `not_observed`, 통제 SHA는 null입니다. 이는 원본 앱을 재개했다는 의미가 아닙니다. 수신기와 전송 영수증의 성공은 바이트 수·암호문 SHA가 일치한 미검증 전송만 뜻하며, `backup_verified=false`를 유지합니다.

수신 상한은 2,300,300,288바이트, 초기 여유 공간은 상한에 3GiB를 더한 값, 수신 제한 시간은 2,400초로 유지합니다. 링크·권한·경로 변경과 중복 실행을 거부하고 실패 partial은 보존합니다.

## 검증 및 다음 단계

수신기 합성 검사 38개와 워크플로 경계 검사 18개를 통과했습니다. 여기에는 원래 세션 불변, 새 namespace 누락 시 거부, 실제 합성 소스 수명주기의 출력 대조, 오류 집합 일치, 공개 파일의 SCP 접근 권한, 같은 파일 디스크립터의 해시 검증이 포함됩니다. 독립 읽기 검토에서 P1/P2 문제는 발견되지 않았습니다. 이 결과는 실제 서버의 보존·복구 검증을 대신하지 않습니다.

최종 소스·archive 수정·경로 필터를 조립한 정확한 커밋의 CI와 공개 진단을 확인한 뒤에만 새 세션을 실행합니다. 서버 B에서 독립 회수한 암호문의 전체 바이트 수·SHA를 대조하고, 인증된 복호화와 기존 논리 세션의 자료 복구 검사를 별도로 수행합니다. archive 및 복구 결과의 `application_restore_verified=false`를 유지하며, 제품 실행 복구를 시험했다고 표현하지 않습니다. ERP 반영과 최종 철거는 이 검증 결과에 따라 별도 조정합니다.
