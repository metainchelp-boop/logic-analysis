# 직원 관제 진입과 전체 계정 수집 개선

## 승인 및 현재 근거

대표가 2026-10-02 「내 컴퓨터에서는 접속이 되는데 직원들 컴퓨터로는 안되나봐 크롬으로 사용하고 있어. 개선 순서대로 진행해.」라고 구현을 지시했다.
앞서 제안한 순서(직원 진입 → 무활동 확인 → 날짜 경계 공정성 → 제한 내 처리량)를 유지한다.
이번 승인은 코드 개선·검증이며, 운영 배포·재시작·권한 확대 승인은 아니다.

운영 기준 소스는 `d6542c37`, 작업 시작 HEAD는 봉인 도구를 포함한 `91a0f7a`이다.
대표의 전산 메뉴 새 로그인은 실제 Chrome에서 성공했다. 관리 직원 두 명의 로그인 실패는 신고된 사실이며 직원 PC에서 HTTP 실패 단계는 아직 확인하지 못했다.
현재 같은 장애 문구가 인증 창 연결 실패, 전산 교환 실패, 조직 자료 오류를 합쳐 보여준다. 이 불명확성은 실제 화면 코드를 사용하는 합성 시험으로 재현할 수 있지만 직원 PC 장애의 특정 원인 증명은 아니다.

## 선택한 좁은 변경

### 1. 로그인 실패를 구별한다

- 창 연결, 출처 검증, 요청 형식, 암호 기능, 전달 시간 초과, 전산 응답, 낡은 조직 자료를 고정된 진단 코드와 한국어 안내로 분리한다.
- 토큰·교환 코드·참조 주소·원문 응답·개인정보·예외 문자열은 화면과 로그에 노출하지 않는다.
- 출처 허용 목록, 부모 창 검사, 메시지 발신자/요청 번호, 일회용 코드, PKCE, 서버의 직원 담당 범위는 그대로 둔다.
- 임의로 출처를 추가하거나 인증 검사를 완화하는 방식은 선택하지 않는다.
- 실제 직원 오류 원인이 확인되기 전에는 이를 직원 접속 해결 완료로 표시하지 않는다. 배포 후 진단 코드로 정확한 실패 단계를 확인하고 그 원인만 후속 수정한다.

### 2. 실제 무활동과 불완전한 통계를 구분한다

- 신선한 요약 통계에서 누락된 캠페인에 한해 같은 날짜의 일별 자료를 확인한다.
- 일별 날짜·지표가 모두 완결되고 값이 0인 경우에만 무활동 0으로 인정한다.
- 지연·누락·해석 불가·요약과 불일치하는 비영 값은 계속 미확인이다.
- 추가 조회 및 내부 재시도도 기존 HTTP/시간 예산을 사용하고, 매 요청 직전 현재 이관 권한을 검사한다.

### 3. 날짜가 바뀌어도 오래 대기한 계정이 먼저 기회를 얻는다

- 당일 성공·인증 확인 필요·재시도 소진 제외, 재시도 가능 시각, 현재 수락 목록 유효성은 유지한다.
- 조회 후보는 이력이 없는 계정, 전체 날짜의 마지막 시도가 오래된 계정 순으로 고른다. 같은 시각만 계정 번호로 정리한다.
- 당일 미시도라는 이유로 전날 처리한 저번호 계정이 오래 대기한 꼬리를 계속 추월하지 않게 한다.
- 전날 수치나 부분 합계를 오늘 결과로 옮기지 않는다. 일별 결과와 캠페인 체크포인트는 기존 날짜별 계약을 유지한다.
- 새 스키마나 운영 데이터 보정은 추가하지 않는다.

### 4. 기존 요청 예산을 사용한다

- 3계정 고정 중단 대신 최대 24후보 중 기존 회차 HTTP 24회/30초 예산에 들어오는 계정까지 순차 처리한다.
- 계정별 8회/10초, 기존 초당 3회 제한, 60초 회차 간 대기, GET 전용, 공급자 오류 재시도 제한은 유지한다.
- 다음 계정의 최소 읽기에 모자란 예산은 불필요한 실패 시도로 소진하지 않는다.
- 병렬 스레드, 간격 단축, 실제 네이버 호출 상한 확대는 이번 안에 넣지 않는다.
- 속도 개선은 동일한 합성 계정/응답/시계로 전후 비교한다. 운영 전체 완료시간으로 환산해 보장하지 않는다.

## 검증 및 완료 조건

1. 실제 로그인 수신/화면 코드의 실패 분기 회귀 시험과 기존 인증 거절 시험.
2. 완결된 0, 누락 일자, 지연 자료, 비영 값, 중간 이관 회수, 요청 예산 회귀 시험.
3. 자정 전후와 여러 날 동안 제한된 회차를 반복해 꼬리 계정이 기회를 받는지 확인.
4. 고정된 정상/빈 계정 집합에서 같은 24회 예산의 완료 수와 HTTP 수를 비교.
5. Linux의 원래 파일 잠금으로 전체 테스트, 격리 실제 브라우저, 컨테이너 검사. macOS의 파일 잠금 충돌을 제품 변경으로 우회하지 않는다.
6. 코드 검증과 운영 배포, 대표 브라우저 확인, 직원 실로그인, 운영 처리량 실측은 각각 별도 결과로 보고한다.

## 적용 계획

1. 진입 실패 재현 시험 → 안전한 진단 코드 → 인증 경계 검토.
2. 무활동 재현 시험 → 누락분 일별 0 검증 → 기존 무활동/미확인 시험.
3. 자정 기아 재현 시험 → 마지막 시도 순서 → 날짜·재시도 회귀.
4. 3계정 중단 재현 시험 → 회차 예산 활용 → 합성 전후 처리량 및 전체 Linux CI.
5. 독립 검토 후 개발 브랜치에 결과 보관. 운영 적용은 별도 승인 후 진행한다.
