# 네이버 계정 우선 관제 — 승인된 개발 범위

승인 근거: 2026-10-02 대표 요청. 회사에 이관된 모든 계정을 먼저 수집하고 전산 업체와 매칭한다. 기존 계약 기반 점검 결과는 보존한다. 운영 배포·광고 변경·자동입찰·보고서 발행은 이번 개발에 포함하지 않는다.

## 화면과 권한

- 계정 원장은 현재 대행 연결 전체 목록을 기준으로 고객 번호당 한 줄이다. 전산 매칭/업무 단계/읽기 수집 상태를 별도 표시한다.
- 진행중·전략관리·사후관리·재계약진행중·환불중·홀딩중·환불완료·계약만료를 전산 실제 단계로 표시한다. 모르는 단계는 미분류이다. 날짜만으로 전산 단계를 바꾸지 않는다.
- 전산 전체 목록이 완전하고 최신인 때에만 미등록 후보를 분류한다. ‘전산 내에 등록된 업체 정보 없음’은 연결 가능한 업체를 찾지 못했다는 뜻이며 실제 미등록 여부는 확인이 필요하다는 설명을 붙인다. 동명이인·복수 후보·번호 충돌·원본 부족은 미분류로 남긴다.
- 대표는 전체와 미매칭을 본다. 재직 관리부서 직원(팀장 포함)은 본인 주/부/유효한 직전 담당 범위만 본다. 다른 부서·퇴사자·관리부서 여부 미확인은 접근을 거절한다.
- 부서는 팀명이나 팀장 여부가 아니라 전산 authority.departmentType == MANAGEMENT로 판정한다. 직원 선택은 부서 계층 없이 재직 관리직원만, 대표는 전체 목록·직원은 본인만 제공한다. 숫자는 실제 현재 이관된 계정을 중복 없이 센다.
- 숨김 단계와 조직 담당 근거가 없는 업체는 직원에게 노출하지 않는다. 목록·직접 상세·후보·알림·선택 범위 모두 서버에서 검사한다.

## 자료와 수집

1. BE에 엔진 전용 키로만 읽는 전체 업체 catalog 경로를 추가한다. 기존 contracts/고객 ID/자격 입력 계약은 변경하지 않는다. catalog는 계약/담당/단계 필터 없이 ID·상호·실제 단계·숨김/단계 유효 여부만 반환한다.
2. catalog와 기존 숫자 ID 자료를 원자적으로 캐시한다. 전산 조회가 일부 실패하거나 총수·중복·시각 검증이 실패하면 이전 수락본을 보존하며 현재 결과를 정상처럼 표시하지 않는다.
3. 저장된 광고 계정 ID를 현재 회사 대행 목록의 Customer ID로 풀어 매칭한다. 사람 확인을 우선하고 이름 후보만으로 확정하지 않는다. 한 원천 계정을 복수 계약에 중복 귀속하지 않는다.
4. 새 읽기 수집기는 전산 등록·계약 만료 여부와 독립적이다. 최신 완전 대행 목록에 현재 있는 계정만 별도 서명된 읽기 권한으로 접근한다. 철회·권한 거절·목록 노후화는 수집 중단/실패 사유로 남긴다.
5. 원천 계정×일자 수집 결과는 기존 계약별 점검/성과 귀속 이력을 덮어쓰지 않는다. 계정당 체크포인트, 회차 호출·시간 상한, 공정한 순환, 제한된 재시도를 사용한다. 기능 스위치는 기본 OFF이다.

## 검증 및 반영 순서

1. 실패 테스트: 미등록/만료/환불완료 누락 방지, 동일 계정 중복 제거, 불완전 전산 목록 오분류 방지.
2. 권한 테스트: 타부서·퇴사·타인 담당 URL/필터/알림·직원 수·후보 노출 차단, 0번 대표 유지.
3. 격리 수집 테스트: 미매칭도 읽기, 철회/오래된 목록은 호출 0, 재시작/재시도·예산 상한, 기존 이력 보존.
4. API·화면 회귀와 독립 검토. 실제 네이버 광고 쓰기 호출은 0.
5. 운영 반영은 별도 승인 후 BE catalog/조직 필드 → 엔진/화면 → 새 수집 스위치 → 전체 수량 대조 → 직원 실로그인 순서로 한다. 단위/합성 검증을 실사용 완료라고 보고하지 않는다.

## 제외

Safari, 자동화 실행, 보고서 작성/발행, 기존 API 키 재입력, ERP 업체 자동 생성, 업무 단계/담당자 자동 변경, 고객자료 외부 반출은 제외한다.
