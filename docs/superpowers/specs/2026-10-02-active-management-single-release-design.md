# 실관리 중심 네이버 관제 — 통합 개발·단일 배포 설계안

## 상태와 최신 지시

2026-10-02 대표의 최신 요청을 반영한 설계안이다. 제품 코드·운영 설정은 아직 바꾸지 않았다. 아래 확정 방향을 이전 전체 이관 계정 자동 통계 수집, 월간 5일 생성, 단계별 배포보다 우선한다. 업무 선택 C는 답변으로 확정했고 남은 선택 A·B는 문서 마지막에 분리했다.

- 실관리 광고주에 자동 수집을 집중하고, 환불중·홀딩중·계약만료 등 비관리 이관 계정은 수동 조회로 분리한다.
- 이관 전체 목록과 실제 관리 중인 전산 업체의 누락 점검은 유지한다.
- 수집 시도 상태와 마지막 확인된 실적을 따로 표시한다. 미수집을 0으로 만들지 않는다.
- 주간은 월~일을 다음 월요일, 월간은 1일~말일을 다음 달 1일에 볼 수 있게 한다.
- 매칭 사유와 네이버 광고 원천 사유를 구체적으로 보존한다.
- 직원 Chrome 문제는 별도 작업이다. 광고 자동화 탭 및 그에 따른 안전장치 고도화는 가장 마지막에 대표와 별도 심층 설계한다.
- 이번 범위를 모두 개발한 뒤 통합 검증하고 한 번에 배포한다. 기능별 중간 배포는 하지 않는다. 기존 권한·광고 쓰기 금지·기본 복구 보호를 없애는 뜻은 아니다.

## 현재 코드에서 확인한 공백

1. `store.py:inventory_work`는 현재 이관 여부만 자동 후보 조건으로 쓴다. 월간 후보도 실관리 단계를 검사하지 않는다.
2. `handles.py:MONITORED_STAGES`는 매칭·미리보기·아침 점검 등이 공유하므로 단순히 그 상수를 줄이면 다른 기능도 달라진다.
3. `inventory.py`는 이관 계정부터 목록을 만든다. 전산 관리 업체의 계정 연결 자체가 없으면 이 목록의 분모에서 누락된다.
4. 당일 수집 행만 표시하므로 과거 정상 실적을 재시도 중에 따로 보여 주는 경로가 없다.
5. 원장 일자는 점검일이고 지표는 전일 실적이다. 캠페인 일별 표는 실제 실적일이다. 날짜를 그대로 혼용하면 하루가 밀린다.
6. 아침 점검은 비교 구간을 읽어도 어제만 저장한다. 월간 경로는 매일 기간 합계를 조회하며, 월말 마지막 날을 포함한 전월 닫힌 기간 보고서는 만들지 않는다.
7. 매칭 상세 차단 사유가 원장에서는 `MATCH_REVIEW`로 합쳐진다. `STATUS_FROM_AUDIT`는 네이버 광고 반려가 아니라 수집 작업 복원 때 상세 사유가 사라지는 별도 문제다.

## 1. 전체 이관과 실관리 대상을 분리

- 전체 이관 원장은 계속 보관한다. 관리계정·하위계정 목록 확인은 계정별 성과 조회와 분리한다. 모든 이관 계정의 캠페인·잔액·성과를 자동으로 읽는 방식은 종료한다.
- 전산 관리 업체 목록을 반대 방향으로도 대조한다. 업체 수와 광고계정 수를 구분하며, 관리 업체가 계정 연결 누락 때문에 조용히 사라지지 않게 한다.
- 자동 후보는 최신 전산 단계, 확실한 매칭, 유효한 현재 대행 권한, 관제 관리 제외 여부를 함께 확인한다. 후보 선정과 실제 호출 직전에 같은 판정을 쓴다.
- 권고 기본 단계는 진행중·전략관리·사후관리·재계약진행중이다. 환불중·홀딩중·환불완료·계약만료는 수동만, 단계·매칭 미확인은 확인 필요이다. 정확한 포함 단계는 선택 A를 따른다.
- 광고비가 어제 0이었다는 이유로 관리 대상에서 빼지 않는다. 광고가 중지된 관리 업체도 점검 대상이어야 한다.
- 관제 포함·제외는 전산 계약 단계나 담당자를 바꾸지 않는다. 제외·복귀 사유, 행위자, 시각을 남긴다. 제외 단계 업체를 임의로 자동 승격시키지는 않는다.
- 원장 전체 수와 자동 수집 대상 수를 별도 표시한다. 수동 전용을 영구 수집 대기로 계산하지 않는다.
- 비관리 업체는 자동 성과 점검이 없으므로 잔여 광고비 발생도 자동 탐지되지 않는다는 점을 화면에 알린다. 네이버에서 실제 광고를 정지하거나 대행 해제하는 기능은 이번 범위가 아니다.

## 2. 수집 작업량과 내부 제한 개선

- 종전 전일 18회/월간 6회 고정 배분안만으로 해결하지 않는다. 실관리 대상 축소, 일별 결과 재사용, 중복 통계 호출 제거를 먼저 적용한다.
- 기존 24호출/30초·최소 60초 간격은 내부 보호 설정이다. 네이버의 공식 고정 할당량으로 설명하지 않는다.
- 새 자동 대상 수, 회차 실제 호출 수, 응답 지연, 재시도, 429 발생을 계측해 불필요한 대기와 작업 예산을 검토한다. 제한을 무제한 해제하거나 측정 전 개선 배수를 약속하지 않는다.
- 자동 전일 수집, 구조 점검, 과거 누락 채움, 수동 1회 요청은 공유 제어 아래 서로 굶지 않도록 제한된 처리 기회를 가진다. 수동 연타가 자동 작업을 밀어내지 않게 중복 제거·대기·계정별 권한을 검사한다.
- 429·인증 실패·철회·목록 이상·오래된 조직/단계는 각각의 중지/대기 규칙을 유지한다. 장애 보호를 우회하는 병렬 호출은 하지 않는다.

## 3. 수집 상태와 실적 표시

- 별도 필드: 현재 수집 상태, 마지막 시도 시각, 다음 시도 시각, 마지막 정상 실적, 실적 기준일, 성공 수집 시각, 원천 기준시각(제공될 때), 최신화 여부.
- 처음이면 `수집 대기 / 아직 수집된 자료 없음`이다. 재시도 중에는 `대기 중(재시도)`와 마지막 정상값을 보여 준다.
- 어제 실적이 없고 그 이전 자료만 있으면 해당 실적 날짜를 표시한다. 이를 어제 실적으로 이름 붙이지 않는다.
- 비즈머니는 조회 시점의 잔액이며 전일 성과와 다르므로 별도 시각을 표시한다.
- 실패한 새 요청이 마지막 성공 자료를 지우지 않는다. 과거값은 참고 표시만 하고 현재 완결 집계·정상 판정에는 섞지 않는다.
- 권한 철회·담당 범위 변경·계정 재연결 때는 이전 업체의 자료가 남지 않게 현재 권한과 귀속을 다시 검사한다.

## 4. 일별 원장과 주간·월간 보고서

- 계정/캠페인/실적일별 저장 자료를 집계의 기준으로 삼고, 필요한 전환 지표와 일별 완결성 증거를 함께 보관한다. 기존의 기간 합계를 일별로 임의 배분하거나 누적 월합계를 중복 합산하지 않는다.
- 대시보드·주간·월간은 같은 집계를 재사용한다. 화면 조회는 저장된 자료만 읽고 네이버 재호출을 일으키지 않는다.
- 주간: 한국시간 월요일~일요일, 다음 월요일 기존 10시 생성 일정 유지. 월간: 한국시간 전월 1일~말일, 다음 달 1일 아침 수집 뒤 생성한다. 월간 기존 5일 일정은 대체한다.
- 생성일에 항목을 만들되 자료가 부족하면 `수집 중/부분 집계`를 명시한다. 누락 날짜·계정·지표와 최신화 시각을 표시하고 완성 보고서처럼 자동 게시하지 않는다.
- 게시 전 계정 확정, 기간 완결, 담당 권한, 기존 비용 공개 설정을 검증한다. 주간 열린 이슈가 있으면 담당 검토, 월간은 담당 검토라는 기존 규칙은 유지한다.
- 첫 연결 시 이번 달과 직전 주간 등 필요한 빈 날짜만 제한된 작업으로 채운다. 이미 수집된 확실한 과거 자료는 다시 전부 읽지 않는다. 과거 자료를 채웠다는 실측 전 완성을 주장하지 않는다.
- 늦게 정정된 원천 자료는 해당 날짜와 관련 집계만 갱신한다. 게시본을 조용히 덮어쓰지 않으며 수정 이력과 재검토 상태를 둔다. 잠정본 정책은 선택 B를 따른다.
- 이미 관리하던 기간의 저장 실적은 현재 환불/만료로 바뀌어도 과거 보고서에서 지우지 않는다. 과거 관리·매칭 기간을 확인할 근거가 없으면 미확인으로 둔다. 수동 전용 계정의 새로운 자동 API 호출을 과거 채움이라는 이름으로 실행하지 않는다.
- 월간 유료 AI 호출은 기존에 확인된 비용 승인 없이 실행하지 않는다. 숫자·고정 문장 보고서와 AI 호출의 운영 활성화는 구분한다. 광고주에게 새 메시지나 공개 링크를 임의 발송하지 않는다.

## 5. 관리 현황과 정확한 사유

- 관리 업체 기준: 연결 완료, 번호 누락, 번호 형식 오류, 번호 충돌, 후보 복수, 전산 정보 미확인, 이관 미확인, 수동 제외를 구분한다. 전체 이관 기준 목록도 유지한다.
- 직원 입력 정본은 기존 전산 광고주 관리의 계정 정보다. 부족한 번호는 그 입력 경로로 안내하고, 연결 대조 결과·보류 사유·다음 조치를 관제에서 보여 준다. 이름만으로 확정하거나 기존 확정을 덮어쓰지 않는다.
- 매칭 사유, 광고 상태 사유, 수집 실패 사유를 별도 보관한다. 네이버가 실제 제공한 코드와 한국어 의미, 대상 계층, 확인 시각을 연결한다.
- 캠페인뿐 아니라 그룹·소재·키워드·사업채널 등 현재 API로 확인 가능한 계층의 상태와 상위 원인을 함께 확인한다. 중지·기간 대기/종료·예산·검수·연동·타겟 오류 등을 단순한 점검 불가로 합치지 않는다.
- 알려지지 않은 새 코드는 원문 코드와 `해석 미확인`, API에 상세가 없으면 `상세 사유 미제공`으로 남긴다. 제공되지 않는 원인을 추정하거나 모든 상태를 긴급으로 올리지 않는다.
- 수집 복원 기록의 상세 사유도 보존한다. 이미 저장되지 않은 과거 사유를 복원했다고 주장하지 않는다.
- 대표 전체/재직 관리직원 본인 담당 열람은 유지한다. **대표 답변 C 확정: 관리직원은 본인 담당만 연결 확정·관제 포함/제외할 수 있고 번호 충돌·타 담당 충돌은 대표 확인으로 보낸다.** 범위는 서버에서 조작 직전 재검증한다. 대표 검증 모드의 전역 쓰기 차단을 통째로 풀지 않고, 승인된 관제 연결·관리 분류 조작만 제한적으로 허용한다. 네이버 광고 변경과 전산 계약/담당 수정 권한은 추가하지 않는다.

## 6. 통합 검증과 단일 배포

1. 대상 분리·수동 조회·일별 자료와 표시를 개발한다.
2. 관리 업체 누락 대조·매칭 사유·광고 구조 사유를 연결한다.
3. 주/월 집계·월경계·생성 및 검토 화면을 연결한다.
4. 단위/실제 저장소/서버 조립/권한/API/브라우저 통합 시험과 독립 검토를 모두 수행한다.
5. 검증된 버전 하나와 호환 데이터 변경을 묶어 한 번 배포한다. 기존 배포 전 사본·호환 복구·단일 쓰기·권한·네이버 GET 전용 보호는 유지한다.
6. 배포 뒤 실관리 대상 분모, 완료 증가, 원천 표본 대조, 정확한 사유·시각·보고서 기간을 확인한다. 첫 자료 채움과 화면 배포 성공을 별도 보고한다.

필수 회귀: 미매칭 업체 누락, 같은 계정 복수 귀속, 후보 5개 초과, 단계 전환 도중 호출 중단, 미확인 단계, 수동 중복, 제외·복귀, 정상 0과 누락, 재시도 중 과거값, 담당 변경 자료 잔류, 전월 말일·윤년·주월 경계, 부분 캠페인/전환 자료, 재시작 사유 보존, 429와 기존 서비스 영향.

이번 제외: 직원 Chrome 접속 원인 해결, 실제 광고 변경/자동입찰, 자동화 전용 심층 안전 설계, 새로운 유료 AI 지출 승인. 기존 알림·공유 기능은 임의로 스위치를 켜지 않는다.

- B. 다음 달 1일 보고서: 잠정 생성 뒤 자료 보완·수정 이력 유지(권고) / 생성본 고정·수정본 수동 생성.
- C. **확정:** 관리직원도 본인 담당만 확정·포함·제외, 충돌은 대표 확인. 대표의 비동기 질문 답변(2026-10-02)을 근거로 한다.

## 확인한 외부 근거

- 네이버 공식 API FAQ: 호출 총량 고정 제한과 계정별 동적 속도 제한은 다르며, 속도 초과는 429로 알려 준다. `status`/`statusReason`은 상위 계층 상태와 함께 확인할 수 있다. https://github.com/naver/searchad-apidoc/wiki/FAQ
- 네이버 대용량 보고서 도움말: 성과 지표가 48시간 이내 변경될 수 있음을 안내한다. 이 안내를 현재 `/stats`의 모든 지표에 대한 영구 확정 시점 보장으로 확대하지 않는다. https://ads.naver.com/help/faq/1239
- 전환 추적 도움말: 광고 중지 뒤에도 전환이 집계될 수 있으며 현재 문서는 전환 발생일 기준 예시를 제공한다. 과거 문서의 일률적인 14일 소급 계산 가정을 그대로 재사용하지 않는다. https://ads.naver.com/help/faq/1215
