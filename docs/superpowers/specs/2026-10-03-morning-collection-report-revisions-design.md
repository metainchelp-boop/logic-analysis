# 출근 전 집계·실적 정정·전체폭 화면 설계

## 상태와 승인 범위

- 기준 코드: `f86f4e5` (운영 배포 기록의 `657d98d`와 제품 코드 동일).
- 대표 승인: 00:01 전일 수집 시작, 10:00 출근용 집계 목표, 10시 미완료 건 계속 수집. 전체 탭 전체폭·가로 스크롤 없는 반응형 개선 요청 유지.
- 이번 추가 문의: 나중에 바뀐 실적을 감지·정정하여 주간·월간 보고서가 어긋나지 않게 할 수 있는지.
- 이 문서는 위 승인과 새 정정 정책 제안을 구분한 설계서다. 새 정정 정책은 검토 대기이며 제품 코드·운영 설정·DB·배포를 변경하지 않았다.
- 원칙: 전체 구현·검증을 묶어 한 번 배포한다. 직원 PC Chrome 진입, 자동입찰·광고 수정, 외부 보고서 발송·알림, ERP 계약·담당 원본 변경은 제외한다.

## 1. 확인한 현재 구조

1. 기존 morning 점검은 06:30~08:00이다. 새 managed performance 경로는 시간창 밖에도 실행되나 같은 tick에서 기존 점검이 먼저 동기 실행되어 지연시킬 수 있다. UI는 이 둘을 혼동하게 표시한다.
2. 전체 tick 종료 뒤 60초 대기한다. 실적·구조 회차 한도는 합산 24호출/30초, 실적 최대 18호출/20초, 계정 8호출/10초, 초당 3회다. 이관 목록·기존 morning까지 모두 합산한 전역 예산이라는 뜻은 아니다.
3. `STATS_INCOMPLETE`도 retry 네 번을 소진하면 limited가 된다. 자정 원천 집계 대기와 실제 장애를 분리해야 한다.
4. 계정·실적일 단일 일별 원천, 이전 값 이력, 날짜별 값/완결 상태 지문, 보고서 새 판 생성 및 옛 승인 비승계는 존재한다.
5. 완결된 날짜의 일반 정기 재확인은 없다. 전환 미완결 재조회는 2시간 간격·해당 행 누적 네 번이며 일일 네 번이 아니다. 전월 3일 재확인도 완료하면 계속 반복하지 않는다.
6. 보고서 재집계는 지난달 1일이 속한 기간부터다. 오래된 날짜 변경, 새 응답의 원천시각 역행, 주간·월간 동시 판 전환을 충분히 처리하지 않는다.
7. 실제 운영 화면 1,920px에서 본문은 1,180px이고, 이관 표 표시 영역 1,146px·내용 1,616px로 내부 가로 스크롤이 있다.

## 2. 출근용 수집 — 승인된 방향

- 기준 시간대는 한국시간이다. 00:01부터 전일 기본 실적을 우선 확보하고 10:00에 확보 자료·완료/부분/대기/오류 현황을 제공한다. 10시는 강제 중단이 아니다.
- 미완료는 체크포인트를 보존해 계속 수집한다. 날짜가 바뀌어도 작업의 원래 실적 기간은 바꾸지 않는다. 권한·이관·매칭·귀속·캠페인 목록은 계속 재검증한다.
- 집계 대기는 실제 HTTP/인증 오류와 다른 원인으로 표시하고 15분→30분→60분 간격으로 재확인한다. 네 번의 장애 재시도를 이 대기로 소진하지 않는다. 같은 계정·목적·기간 중복을 막고 과거 미완료는 보충 대상에 합쳐 대기열을 무한히 늘리지 않는다.
- 429·인증 만료·권한 회수·원천 불일치의 기존 중단 조건은 유지한다. 집계 대기로 오분류하여 보호 장치를 우회하지 않는다.
- 자정에 유효한 조직·전산·이관 목록을 확보하는 경로와 기존 morning의 직렬 간섭을 조정한다. 기존 경보와 타 서비스 08:00/08:30 자원 사용은 임의 활성화·확대하지 않는다.
- 일일 4단계, 자동 단계 전환, 비관리 일요일 조회, 담당자 본인 권한·충돌 대표 확인을 유지한다. 계정 수를 상수로 고정하지 않는다.

## 3. 사후 정정 정책 — 검토 요청안

### 대안

- 최근 3일만 재확인: 호출 부담은 작지만 늦은 전환을 놓칠 수 있다.
- **권고: 최근 3일 매일 + 최근 31일 주간 대조 + 보고기간 재확인**: 전일 수집을 우선하면서 늦은 변경을 찾고, 자동 범위 밖은 명시적인 기간 재확인으로 처리한다.
- 과거 전체를 매일 재확인: 원천 보존 한계와 호출 비용이 커 이번 범위에서 채택하지 않는다.

### 주기와 대상

| 목적 | 범위·주기 | 대상·우선순위 |
|---|---|---|
| 전일 최초 집계 | 매일 D-1 | 실관리 4단계, 최우선 |
| 최근 수정 감지 | D-3~D-1 하루 한 회차 | 실관리, 전일 최초 집계 뒤 |
| 지연 전환 등 대조 | 매주 일요일 D-31~D-1 한 회차 | 실관리 및 현재 조회 권한이 유효한 과거 관리 보고서 계정. 비관리의 이 대조는 일요일에만 시작 |
| 주간 생성 전 | 월요일 00:01부터 직전 월~일 | 실관리 계정의 새 회차. 같은 날짜의 재확인 결과를 재사용, 월요일 10시 초판 목표 |
| 월간 생성 전 | 매월 3일 00:01부터 전월 전체 | 실관리 계정의 새 회차. 최대 31일, 3일 10시 초판 목표 |
| 자동 범위 밖 | 권한 있는 직원의 계정·기간 재확인 요청 | 한 작업 최대 31일, 중복·재요청 간격 제한, 현재 조회권한과 과거 귀속 모두 검사 |

비관리 전체의 일요일 최근 7일 점검은 유지한다. 같은 계정의 31일 대조가 이를 포함하면 원천을 재사용하며, 7일 점검 표시와 31일 정정 대조의 목적·기간을 혼동하지 않는다. 일요일 회차가 월요일로 넘어가도 이어 수집하되 새 회차를 중복 생성하지 않는다.

비관리 과거 보고서 계정은 월요일·매월 3일이라는 이유로 평일 자동 조회를 새로 만들지 않는다. 일요일의 해당 기간 확인 결과·저장 자료로 보고서를 만들고, 해당 보고기간 재대조가 끝나지 않았거나 확인하지 못한 날은 그 상태를 표시한다. 직원의 명시적 수동 조회는 기존 권한 안에서 별개다.

31일은 자동 감시 범위이지 네이버 수치의 영구 확정 기한이 아니다. 정정 대조가 미완료이면 해당 보고서에 마지막 대조 시각과 미완료 상태를 표시한다. 월간 3일 생성도 이후 수정이 불가능한 확정본을 뜻하지 않는다.

## 4. 저장·보고서 정합성 계약

1. 기존 `performance_job → run_performance → daily_performance` 경로를 확장한다. 수집 목적·고정 기간·재확인 세대를 명시하고, 새 세대는 완료 progress를 재사용하지 않는다. 같은 세대 안에서만 이어 읽는다.
2. 날짜별 실제 원천을 다시 읽는다. 기간은 최대 31일이고 월 경계를 허용한다. 신규 worker나 별도 호출 예산은 만들지 않는다.
3. 값·완결 증거가 달라지면 일별 정정 이력과 원천 버전을 기록한다. 숫자 정정 버전과 재검증 메타데이터를 분리한다. 값이 같아 새 정정본이 없더라도 마지막 성공 대조 시각·마지막 시도·대기/실패 상태는 갱신한다.
4. 오래된 원천/체크포인트가 더 최신값을 덮지 못하게 한다. 단순 금액 증가 조건을 사용하지 않는다. 검증된 감소·명시적 0도 정상 변경이다. 실패·누락을 0으로 치환하지 않는다.
5. 현재 전환이 미확인인 경우 이전 전환 성공값을 최신 기본지표와 섞어 완결로 표시하지 않는다. 이전 값은 이력으로 보존한다.
6. 변경된 실적일이 속한 주간·월간을 직접 찾아 정정 대상을 등록한다. 지난달 한정 생성 루프에만 의존하지 않는다. 과거 귀속을 현재 매칭으로 소급 변경하지 않는다.
7. 같은 업체의 영향받는 보고서들은 동일한 원천 버전으로 계산하고 묶어 교체한다. 계산 중에는 정정 대기/갱신 중을 표시하며 이전 판을 최신 재검증본으로 오인시키지 않는다. 중간 실패 후 재개해도 일부 기간만 최신이라고 노출되지 않도록 검증한다.
8. 이전 보고서를 덮어 지우지 않고 판 번호·정정 시각·변경 지표/차이·원천 재확인 시각을 표시한다. 현재 없는 이전 판 조회 API/화면은 읽기 전용·페이지 분할·기존 업체 열람 권한 검사로 추가한다. 새 판에는 옛 검토 승인을 승계하지 않는다. 해당 보고기간의 요구된 재대조가 미완료인 동안 새 검토 승인은 막고, 과거 승인은 당시 판의 기록으로만 보존한다. 외부로 내려받은 사본이 자동 수정된다고 안내하지 않는다.
9. 일별·주간·월간은 같은 계정·실적일·지표 정의·한국시간을 사용한다. 월간을 월 경계가 다른 주간 보고서 전체의 합으로 계산하지 않는다. 광고비·노출·클릭은 일별 합계, ROAS 등 비율은 합계 분자/분모로 다시 계산한다.

## 5. 호출 안전·처리량

- 짧은 기간/긴 기간 모두 캠페인별 기간 조회를 활용한다. 3일을 날짜별 세 번 호출하지 않는다. 단, 추가 재확인 회차와 긴 응답의 시간·크기 비용은 있으므로 무료나 즉시라고 설명하지 않는다.
- 실적 18호출/20초 안에서 보충·재확인에 최대 6호출의 처리 기회를 예약하고 나머지는 최초/미완료 수집에 둔다. 보충 후보가 없으면 기존 실적 한도 안에서 최초 수집이 사용한다. 계정별 기존 한도 및 전체 24호출/30초·회차 종료 후 60초는 보존한다.
- 보고 마감·오래 기다린 작업을 같은 예산 안에서 순환 선정하여 전일 또는 정정 대조가 무한히 밀리지 않게 한다.
- 전체 계정의 오전 10시 완료, 변경 즉시 감지, 감시 범위 밖 모든 변경 발견은 보장하지 않는다. 실제 캠페인 분포·응답시간·원천 지연을 넣어 처리량을 검증한다.

## 6. 전체폭·무가로스크롤 화면

- 6개 탭 공통 본문의 1,180px 최대폭을 해제하고 `width:100%`와 최소 안전 여백을 적용한다. 모달·설명문 등 개별 목적의 최대폭은 일괄 삭제하지 않는다.
- 메뉴·필터·목차·상세 탭을 줄바꿈한다. 좁은 화면에서는 표의 모든 항목을 항목명이 있는 카드/세로 배치로 보여 준다. 열 삭제·금액 축약·작은 글씨·`overflow:hidden`으로 정보 손실을 숨기지 않는다.
- 동적 표에 실제 항목명과 의미 연결을 추가하되 버튼/ID/이벤트를 복제하지 않는다. 기존 디자인·숫자·원문 사유·페이지 탐색·범위 변경 후 늦은 응답 폐기를 유지한다.
- 모달 키보드 동작·초점 복원·담당자 권한·CSP·문자열 안전 렌더링을 유지한다.

## 7. 검증 및 단일 배포 순서

1. 수집 시계·정정 세대·지연 대기 → 00:00/00:01/10:00/자정 이월, 429, 월 경계·윤년·31일, 같은 세대 이어읽기/새 세대 실제 통계 재조회 시험.
2. 원천 수정·보고서 → 값 증가/감소/0, 동일 합계의 날짜 이동, 전환 미확인, 오래된 응답, 과거 보고기간, 재매칭, 검토 승인 비승계, 주간·월간 교체 중 장애/재시도 시험.
3. 예산·우선순위 → 큰 캠페인 계정·일요일 전체 계정·월초 보고 마감 동시 발생·장기간 지연을 합성 시계로 시험. 한도 밖 실제 광고 호출로 부하 시험하지 않는다.
4. 화면 → 320/375/768/1024/1440/1920px × 6개 탭, 사유 펼침·다음 페이지·긴 값·모달·권한별 상태에서 문서와 내부 표/탭의 가로 넘침 0 및 전체 정보 접근 확인.
5. Linux 실제 SQLite/Writer 통합·전체 회귀·브라우저 검증 → 하나의 검증된 앱/스키마 묶음으로 봉인·백업/복귀 준비 → 단일 운영 배포 → 소스/상태/실제 화면 검증. 변경을 적용한 사실과 며칠 뒤 실제 정정 감지 결과는 별도로 보고한다.

## 조사 증거와 한계

- 순수 보고서 및 저장 경계 20개 통과: `PYTHONPATH=backend:. python3 -B -m unittest -v naver_engine.tests.test_reporting naver_engine.tests.test_managed_storage.ManagedStorageBoundaryTest`.
- 전체 managed storage를 macOS에서 실행한 시도는 임시 시험 DB의 WAL 초기화 `database is locked`에서 중단했다. 운영 DB와 관계없고 통합 통과로 세지 않는다. 잠금 우회·보호 해제는 하지 않았다.
- 네이버 검색광고 지표 공지: https://ads.naver.com/notice/25919 — 예외적으로 48시간 이내 성과 정정 가능.
- 네이버 검색광고 전환 도움말: https://ads.naver.com/help/faq/949 — 간접전환 추적 기간 7~20일 설정 안내. 이 설명은 특정 수집 필드의 귀속일·영구 확정 시점을 보증하지 않으며 31일 제안은 운영 감시 정책이다.
