# 이관 현황 잔액 정렬·필터 합계·전산 계정 입력 설계

## 상태·범위

- 2026-10-03 대표 요청 네 가지와 후속 답변 `응 권장안으로 진행해`를 반영한다.
- 승인된 방향: 비즈머니 내림차순, 현재 목록의 확인 잔액 합계, 누락 대조 검색, 기존 전산 열쇠 팝업으로 별도 창 직행.
- 대표가 후속 답변 `응 구현하고 배포해`로 문서·구현·배포를 승인했다. 승인과 실제 구현·검증·배포 완료는 구분한다.
- 기준: 광고센터 체크아웃 `ac8d867`(제품 기준 `e132a4b`), 전산 화면 체크아웃 `20a21f28`, 서버 체크아웃 `543c0d3a`. 전산 파일은 구현 직전에 최신 기준과 재대조한다.
- 수집 정책·네이버 호출·매칭 확정 기준·전산 계약 및 담당자·API 자격·운영 데이터는 변경하지 않는다. 승인된 배포는 아래 변경만 검증 후 순차 반영한다.

## 선택한 방식

기존 전산 창에서 열쇠 팝업을 바로 여는 방식을 사용한다. 관제 안에 별도 입력 팝업과 저장 API를 만드는 대안은 채택하지 않는다. 기존 계정 API는 비밀번호·API 키를 포함할 수 있어 관제가 그 응답을 받지 않도록 한다. 별도 저장소·관제용 계정 정보 복제는 만들지 않는다.

## 1. 이관 광고 계정 전체 정렬

- 현재 서버의 고객 ID 순서를 화면에서 잔액 내림차순으로 바꾼다. 정렬 기준 `비즈머니 높은 순`을 목록에 표시한다.
- 서버가 권한·조회 대상·매칭 상태·업무 단계 필터를 적용한 응답에 기존 검색을 적용한 후, 그 결과의 복사본을 정렬한다. 캐시 원본 배열은 수정하지 않는다.
- 유효한 숫자 잔액은 큰 값부터 표시한다. 0원과 음수도 확인된 잔액이며, 잔액 미확인은 모든 숫자 잔액 뒤에 둔다. 동률은 기존 응답 순서를 유지한다.
- 정렬 때문에 네이버 조회나 전산 저장 요청을 발생시키지 않는다. 기존 행 재사용·변경분 반영·검색어·초점 유지 동작을 보존한다.

## 2. 현재 목록 확인 잔액 합계

- `조회 대상` 선택 상자 바로 옆에 비버튼형 소형 카드 `확인된 잔액 합계 : 1,234,567원`을 표시한다. 상단 전체 현황 카드는 변경하지 않는다.
- 합계 대상은 정렬된 표와 동일한 행 집합이다. 조회 대상, 매칭 상태, 업무 단계, 검색어, 담당 범위를 모두 반영한다. 업체가 같아도 서로 다른 광고 계정이면 각각 포함한다.
- 보조 문구는 `확인 12 / 15계정 · 미확인 3`처럼 합계의 범위를 설명한다.
- 미확인 값은 0원으로 바꾸지 않는다. 대상 0건은 `0원 · 대상 계정 없음`, 대상은 있으나 확인 잔액이 없으면 `— · 확인 잔액 없음`으로 구별한다.
- 원천 확인이 보류되면 `— · 집계 보류`로 표시한다. 권한 오류나 로그인·담당 범위 교체 때 이전 합계도 함께 제거한다. 일시 통신 오류 시 기존 자료를 남기는 경우에는 기존 오류·확인 시각 안내를 유지한다.
- 마지막으로 확인한 잔액은 포함하되 `계정별 확인 시각 기준`을 표시하고, 이전 값이 포함되면 `이전 확인값 포함`을 덧붙인다. 실시간 잔액이라고 표현하지 않는다.
- 서버의 기존 상단 합계와 같이 십진 값들을 먼저 합산한 뒤 원 단위로 한 번 절사한다. 부동소수 오차·비정상 숫자·안전한 표시 범위 초과를 검사한다. 행별 절사 후 합산하지 않는다.
- 좁은 화면에서는 조회 대상과 카드가 줄바꿈한다. 긴 금액이나 문구 때문에 페이지 전체에 가로 스크롤이 생기지 않도록 한다.

## 3. 실관리 업체·계정 누락 대조 검색

- 해당 영역 상단에 독립 검색칸을 추가한다. 업체명·업무 단계·담당자 이름을 공백 정리 및 대소문자 무시 포함 검색으로 찾는다.
- 입력 중 검색하며 `검색 결과 3 / 20업체`처럼 필터 결과를 별도로 표시한다. 기존 실관리 전체·연결·확인 필요 집계는 전체 담당 범위의 뜻을 유지한다.
- 이관 광고 계정 전체의 검색·필터와 서로 영향을 주지 않는다. 두 분류와 다른 탭을 왕복하거나 자료를 갱신해도 같은 로그인·담당 범위에서는 검색어를 유지한다.
- 로그인 종료·교체·담당 범위 교체 때 검색 상태와 이전 결과를 초기화한다. 실제 대상 0건과 검색 결과 0건을 구분한다.
- 응답에 없는 계정 이름·광고 계정 ID를 검색할 수 있는 것처럼 안내하지 않는다. 검색 때문에 비밀정보 API나 네이버 수집 API를 추가 호출하지 않는다.

## 4. ID 미입력 업체에서 기존 열쇠 팝업 직행

### 관제 진입점

- 최신 권한 확인을 통과한 실관리 누락 대조 행 중 `ID_MISSING`이 있는 업체에 `광고 계정 ID 입력`을 제공한다. 원천 보류·권한 확인 전에는 동작시키지 않는다.
- 후보 상태가 우선 표시되어도 `codes`에 `ID_MISSING`이 있으면 대상으로 판단한다. 클릭 시 최신 자료 객체·담당 범위·권한 확인 상태·현재 검색 결과에 여전히 포함된 행인지 재확인한다.
- 업체 식별자는 관제 `possibility_id`와 동일한 전산 가망 업체 번호 `companyIdx`이다. 광고센터 client ID나 계약 번호로 대체하지 않는다. 정수 형식과 현재 행의 소속을 확인한다.
- 버튼은 공식 전산 주소의 `/metapos/advertiser-setup?company=<업체번호>&panel=credentials&vendor=naver`를 별도 창으로 연다. 관제에서 임의 URL·외부 origin·회사명·자격정보를 URL로 전달하지 않는다.
- 기존 공식 전산 주소 `http://metainc.co.kr`를 사용한다. 이번 작업에서 전산 호스트·HTTPS·SSO 체계를 바꾸지 않는다. 해당 주소에 로그인 세션이 없으면 전산 자체 로그인 절차를 따른다.
- 로그인 후 기존 복귀 처리로 업체·팝업 진입 정보가 유지되는지 검증한다. 복귀가 지원되지 않으면 관제로 돌아와 입력 버튼을 다시 누르도록 안내하고, 로그인을 우회하거나 이번 범위에서 SSO를 개편하지 않는다.
- `noopener,noreferrer`로 창을 분리한다. 브라우저가 별도 창을 탭으로 표시해도 기능은 같으며, 열기 실패에 대비해 동일한 안전한 주소로 이동할 수 있는 링크를 제공한다.

### 전산 팝업 재사용

- 기존 `AdvertiserSetupPanel`의 `?company=` 진입 처리에 정확한 `panel=credentials&vendor=naver` 조합을 추가한다. 기존 상세 진입·목록 열쇠 버튼은 그대로 유지한다.
- 직행 처리는 URL의 업체별로 한 번만 수행한다. 닫기·취소에서는 직행용 `panel`·`vendor`를 함께 정리해 자동 재개방을 막는다. 주소 변경으로 다른 업체를 열 때 이전 초안과 팝업 상태를 섞지 않는다.
- 서버에서 업체와 권한을 확인한 뒤, 그 결과의 업체명으로 기존 열쇠 팝업을 연다. 다른 업체의 지연 응답이 현재 팝업·초안을 덮어쓰지 않게 한다.
- 기존 공용 `NaverObservationField`와 저장 핸들러를 사용한다. 별도 계정 정보 UI를 복제하지 않는다.
- 네이버 카드 프리셋은 기존 초안을 보존하고 없는 카드만 추가한다. 전체 초안을 빈 값으로 재설정하지 않는다.
- 명시 벤더가 `NAVER_SEARCHAD`인 매체, 또는 기존 정확한 네이버 이름 판정에 맞는 매체만 선택한다. 매체 번호를 하드코딩하거나 매체 설정을 변경하지 않는다.
- 대상 매체가 하나이고 저장 정보가 없으면 네이버 입력 카드를 초안 상태로 펼친다. 후보가 여러 개면 기존 매체 선택 기능으로 사용자가 고르게 한다. 대상 매체가 없으면 저장을 막고 안내한다. 카드를 여는 것만으로 저장하지 않는다.
- 입력칸에 초점을 주며, 팝업 닫기·취소는 데이터를 변경하지 않는다. 최초 조회 실패·권한 없음은 닫을 수 있는 오류 안내로 표시하고 무한 로딩이나 자동 재요청을 만들지 않는다.
- 기존 서버 권한을 그대로 적용한다. 관제에서 볼 수 있다는 이유만으로 전산 수정 권한을 확대하지 않는다.

### 저장과 관제 반영

- 기존 `PATCH /api/ad-setup/credentials`와 `advertiser_platform_credential.naver_ad_account_no`를 사용한다. 변경된 필드만 보내 기존 로그인 ID·비밀번호·API 고객 ID·키·비밀키를 유지한다.
- 번호 형식은 기존 규칙인 선행 0 없는 양수 숫자 1~15자리다. 저장 실패 시 성공으로 표시하거나 팝업을 자동으로 닫지 않는다.
- 전산에서 실제 저장 성공 응답을 받은 경우에만 `전산 저장 완료 · 관제 반영은 동기화 후 확인`을 안내한다. 관제는 창을 열거나 닫았다는 이유만으로 저장 성공을 추정하지 않는다.
- 창 사이에 토큰·비밀번호·자격정보를 넘기지 않으며 이번 범위에서는 저장 결과를 전달하는 새 메시지 채널도 만들지 않는다.
- 관제로 돌아와 `목록 새로고침`을 누르면 기존에 동기화된 최신 자료를 다시 확인한다. 이 동작이 전산 원본 즉시 동기화나 네이버 재수집을 뜻하지 않는다는 점을 안내한다.
- 기존 동기화·번호 대조·연결 확정 절차를 유지한다. 중복 번호·다른 업체 주장·여러 후보는 임의 확정하지 않는다. 저장 성공이 매칭 성공이나 실적 수집 완료를 뜻하지 않는다.

## 변경 경계와 회귀 검증

1. 광고센터 화면: 잔액 정렬, 정확한 목록 합계, 독립 검색, 허용된 전산 진입 링크. 기본 서버 수집·매칭·DB 변경 없음.
2. 전산 화면: 기존 열쇠 팝업 직행, 네이버 카드 안내, 실패·닫기·지연 응답 처리, 저장 안내. 기존 저장 서버·테이블 재사용.
3. 합성 브라우저 시험: 양수·0·음수·미확인·동률, 필터와 검색 조합, 확인 0건, 합산 후 절사, 이전 값과 원천 오류, 이관 빠짐의 미확인 잔액, 문자열·불리언·NaN·Infinity·개별 및 합계 안전범위 초과, 320/390/820/1280/1440폭 넘침.
4. 권한·상태 시험: 담당 범위 변경·로그인 교체·통신/권한 실패·늦은 응답·캐시 변경분 갱신 시 행·합계·검색·버튼 일치.
5. 전산 입력 시험: 올바른 업체, 네이버 매체 없음/하나/여러 개, 기존 매체/기존 값 보존, 숫자 형식, 실패와 재시도, 취소·닫기, 팝업 차단, 비로그인 진입과 로그인 후 복귀·재진입 안내, 키보드 초점.
6. 합성 저장 요청을 검사해 미변경 비밀정보 전송·관제 origin의 자격정보 수신·토큰 전달·자동 연결·네이버 쓰기가 없는지 확인한다. 운영 업체에 시험 번호를 저장하지 않는다.
7. 기존 계정 정보 상세/열쇠 팝업과 이관 두 보기·상단 카드·관제 접기·검색·변경분 화면 회귀를 실행한다.
8. 구현·자동 시험·브라우저 확인·운영 반영은 각각 결과를 구분한다. 전산 FE가 직행 URL을 지원한 뒤 관제 버튼을 배포하는 순서를 유지하며, 전체 배포는 별도 승인 후 진행한다.
