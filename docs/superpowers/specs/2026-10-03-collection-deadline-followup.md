# 수집 지연 1번 후속 — 내부 비용과 통신 원인을 분리

상태: 순차 개선 지시에 따른 개발·검증 중. 운영 소스 `b83e908`은 이 문서 작성 중 변경하지 않았다.

## 확인 범위

이전 운영 조회(2026-10-03 06:37:03 KST)는 일일 286건 중 완료 116·부분 81·재시도 89였다. 실제 화면의 89건 사유는 `REQUEST_DEADLINE`이었다. 이 수치는 당시 상태이며 현재 전체 수집 완료율이나 개별 원인 분포가 아니다.

기존 `preview-collection-status`는 상태별 건수와 마지막 성공 시각 등을 읽지만 요청별 지연·HTTP 오류·중단 단계를 저장하거나 투영하지 않는다. 과거 89건의 근본 원인을 이 코드만으로 복원할 수 없다.

## 재현한 결함과 좁은 수정

1. **조회 후보를 만들 때 전체 연결 판단을 반복 계산했다.** 실제 `Store`와 메모리 SQLite, 합성 1,793계정/관리 764곳으로 재현했다. 후보와 과거 작업을 하나 만들 때마다 동일 연결 지문을 다시 읽었다. `performance_work`·`structure_work` 각각의 동기 호출 안에서만 한 번 계산하여 전달한다. 전역 캐시나 회차 간 캐시는 만들지 않으며, 매 HTTP 직전 `performance_account_valid`는 그대로 현재 원천을 재확인한다.
2. **권한 확인 이전에 HTTP 잔여 시간을 계산했다.** 권한 확인 동안 마감이 지나도 이전에 계산한 시간으로 요청을 보낼 수 있었다. 권한 확인 뒤 남은 시간을 다시 검사하여 이미 만료되었으면 요청을 보내지 않고, 아직 남았으면 그 시간만 HTTP에 전달한다. 재현 시험 2건이 수정 전 실패·수정 후 통과했다.
3. **통신 오류가 내부 시간 한도로 덮였다.** 합성 503 또는 네트워크 실패에 요청당 1.5초를 부여하면 재시도 3회/7.5초 뒤 다음 대기를 시작하지 못하며 `REQUEST_DEADLINE`만 남았다. 같은 논리 요청에서 확인한 고정 통신 원인과 내부 중단 코드를 분리해서 보존한다. 시간·호출 한도, 재시도 횟수·대기, 성공/부분/실패 정책은 바꾸지 않는다. 성공한 뒤 다른 요청에서 생긴 중단에 과거 통신 원인을 붙이면 안 된다.

## 내부 비용 비교

명령: `PYTHONDONTWRITEBYTECODE=1 python3 tools/naver-store-selection-benchmark.py --history-days 7`

실제 `synchronize_management`·매칭·조직·원천·요청 자격 검사를 사용한다. 합성 데이터만 넣으며 소켓 연결을 차단한다. 파일 DB 잠금·WAL/fsync·실제 HTTP 지연은 포함하지 않는다. 아래 값은 로컬 단일 실행의 근삿값으로 전체 운영 수집 시간이나 개선 배수가 아니다.

| 관리 계정의 완결 작업 이력 | 수정 전 후보 선정 | 수정 후 후보 선정 | 지문 계산 횟수 전 → 후 |
|---|---:|---:|---:|
| 없음 | 1.56초 | 0.09초 | 1,793 → 1 |
| 7일·5,348작업 | 6.21초 | 0.42초 | 7,141 → 1 |
| 30일·22,920작업 | 23.20초 | 2.04초 | 24,713 → 1 |

수정 후 세 조건 모두 실제 수집기를 통한 25캠페인 계정 1곳의 합성 GET 4회·정상 완료를 확인했다. 매 요청 자격 검사는 생략하지 않았다. 조회 후보 준비 시간이 성과 수집의 20초 경과 계산에 포함되므로, 불필요한 준비 비용은 네이버 호출 전에 실제 처리 기회를 소진할 수 있다.

요청별 DB 검증은 같은 합성 규모에서 약 4.3ms/회였으며, 그 비용만으로 25캠페인의 10초 한도 초과를 재현하지는 못했다. 이를 운영의 유일한 원인으로 단정하지 않는다.

## 회귀·배포 경계

- 실제 메모리 SQL 시험에서 계정/이력이 늘어도 전체 연결 판단 조회가 일정하게 유지되는지 확인한다. 수정 전 4개 하위 사례 실패 → 수정 후 통과했다.
- 연결 확인을 새로 기록하면 이전 후보의 자격이 즉시 무효가 되고 다음 후보는 새 지문을 받는 것을 성과/구조 양쪽에서 확인한다.
- 회차 24회/30초, 성과 18회/20초, 계정 8회/10초, 초당 3회, 회차 후 30초와 429 대기는 유지한다. 스키마 11·읽기 전용·원천 완결 검사·기존 성공값 보존도 유지한다.
- 로컬에서 관련 183시험 통과(앞선 125·176시험과 겹치므로 합산하지 않음). 통신 원인 회귀는 서버/네트워크·호출 상한·혼합 원인의 마지막 값·성공 후 다음 요청 분리·429 우선·원문 비노출을 포함한다. Linux 전체 CI 결과는 검증 후 아래에 기록한다.
- macOS 실제 파일 DB 시험은 기존 WAL 잠금 오류로 막히며 잠금을 우회하지 않는다. 메모리 SQL 통과를 파일 DB 검증으로 보고하지 않는다.
- 아직 운영 반영과 개선 후 실계정 완료율 검증은 하지 않았다. 2번 매칭 정리, 관제 판정, 보고서 검증, 직원 Chrome, 자동화 안전 설계는 이번 1번 수정과 구분한다.
