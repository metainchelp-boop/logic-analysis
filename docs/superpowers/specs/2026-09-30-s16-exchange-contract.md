# S16 일회용 로그인 연결 — 구현 계약

2026-09-30. 근거: 네이버 자동운영 설계 §10의 S16 대표 확정(세 입구 모두 일회용 교환 코드), N2ⓐ(네이버 단추 노출은 광고 센터와 동일). 개발만 승인된 상태이며 머지·배포·서버 비밀값 변경은 하지 않는다.

## 공통 계약

- 전산 `POST /api/sso/code`: 직원 Bearer 인증, JSON `{destination,codeChallenge}`. 목적지는 `AD_CENTER`, `LOGIC_ANALYSIS`, `NAVER_CONTROL` 중 하나. 성공은 `{status:200,result:{code,expiresIn:60}}`.
- 코드는 무작위 32바이트의 base64url(패딩 없음, 43자). DB에는 SHA-256 지문·직원 번호·목적지·만료/소비 시각만. 발급 60초 뒤부터 거절. 단회 소비는 DB 원자 연산으로 보장한다.
- 수신 서버가 HTTPS `POST https://api.metainc.co.kr/api/sso/exchange`에 `{destination,code,codeVerifier}` 전송. 목적지별 별도 64자리 hex 키를 `X-Sso-Client-Key`로 전송한다. 기존 계약 동기화 키를 재사용하지 않는다. 전산에는 `SSO_<목적지>_KEY_SHA256` 지문만 설정. 비어 있으면 닫힌다. 광고센터 서버는 `SSO_AD_CENTER_CLIENT_KEY`, 관제 엔진은 `SSO_NAVER_CONTROL_CLIENT_KEY`를 읽는다.
- **브라우저 바인딩(PKCE)**: 코드만 든 링크는 타인의 계정으로 로그인시키는 공격에 이용될 수 있으므로, 받는 창이 무작위 검증자(32바이트 base64url)를 메모리에만 만든다. 전산은 SHA-256 challenge만 받고, 교환 때 검증자가 일치해야 소비한다. 잘못된 검증자로는 코드를 소모하지 못한다.
- 전산은 고정 목적지 새 창을 `?sso_start=<비밀 아닌 요청 식별자>`로 연다. 수신부는 URL을 즉시 정리하고 정확한 전산 origin/opener/요청 식별자를 확인해 challenge를 `postMessage`로 보낸다. 전산도 목적지 origin/창/식별자를 확인하고 발급 코드를 같은 창으로만 보낸다. 수신 뒤 opener를 끊는다. **ERP JWT·코드·검증자 모두 URL에 넣지 않는다.** 직접 `?code=`·새/구 방식 혼합·중복 입력은 거절한다.
- 교환은 키부터 검사하고 본문은 1KB 상한. 다른 목적지·이미 소비·만료·퇴사/비활성은 거절한다. 클라이언트는 redirect·환경 proxy·HTTP 강등·자동 재시도를 사용하지 않는다. 원문 키·코드·응답을 로그/오류에 쓰지 않는다.
- 광고센터·로직분석의 `result`는 `idx,id,name,isManager,authority:{name},teamList:[{idx,parentIdx,name}]`. 기존 로그인 ID를 숫자 idx로 대체하지 않으며 기존 수동 관리자 보존/역할 정책을 그대로 사용한다. 관제는 `idx,isManager,teamList:[{idx,parentIdx}]`만 받는다. 직원 0번은 대표이며 유효하다.
- 응답 `Cache-Control: no-store`, URL은 초기 파싱 즉시 정리. 코드 저장 금지. 실패 시 이전 사용자 세션을 자동 복구하지 않는다. 양쪽 파라미터가 있으면 거절하고 legacy 토큰으로 재시도하지 않는다.

## 전환 순서

1. 발급/교환 서버 + 세 소비부의 오프라인 검증 및 초안 PR.
2. 별도 배포 승인 뒤 목적지별 키를 저장소 밖에서 주입하고 HTTPS·신뢰 IP를 확인. 기존 토큰 경로는 유지한다.
3. 전산 새 입구 배포. 새 링크에는 비밀 없는 `sso_start` 식별자만 넣는다. 관제는 `/session {code,codeVerifier}`만 받으며 실행 스위치는 이번 작업에서 켜지 않는다. 실행 프로그램의 웹 연결은 준비하되, 기본 꺼짐과 키 누락 시 시작 거절을 유지한다.
4. 전산 세 입구 실사용 확인 뒤 별도 차례에 ②·③ legacy `?sso=` 폐기. 같은 날 동시 차단 금지.

## 구현·검증 순서

- 서버 원자 저장소: 만료 경계·중복/동시 소비·목적지·키/비활성·0번 대표 검증.
- 소비부: 외부 교환 seam을 가짜 서버로 검증하고 기존 사용자 권한/로그인 제한을 보존.
- 전산 입구: 버튼 클릭 시 빈 새 창 확보 → 고정 목적지 이동 → 수신 창 challenge 확인 → 인증 발급·코드 전달. 실패/팝업 차단 때 코드를 버리고 안내. 사용자 토큰 URL 유출·임의 redirect 차단.
- 화면: URL 정리가 최초 외부 요청보다 빠른지, 코드 원문이 저장소에 없는지, 혼합/중복 입력 거절 확인.
- 통합: 컴파일/정적 및 격리 테스트. 운영 실사용·실제 서버 키/신뢰 IP 확인과 분리하여 보고한다.
