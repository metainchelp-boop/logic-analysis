# 네이버 쇼핑 SEO 검수 보조 개선 설계

## 1. 승인 범위와 완료 기준

- 대상은 `https://logic.metainc.co.kr/#seo`이며 기존 진단 화면과 관리팀·최고관리자 권한을 유지한다.
- 상품명·판매자 태그·페이지 타이틀·메타 디스크립션의 현재값, 추천안, 수정 이유를 비교한다.
- 직원이 추천을 직접 수정·채택하여 전산에 승인본을 저장·복사한다. 스마트스토어 실제 상품 수정 API는 호출하지 않는다.
- 저장 자료만으로 상위 20개 상품명과 공통어를 분석한다. SEO를 이유로 수집기 설정·수집 시간표·자동 우회·유료 상세 수집을 변경하지 않는다.
- 사내 기준을 재작성하되 기존 내용을 보관하고 사용 기준의 버전을 결과에 남긴다.
- 생성 오류를 운영 로그로 진단한다. 확인한 장애와 원인·복구·배포·실사용 검증을 구분한다.
- 운영 재시작, 설정·비밀값 변경, 본 배포는 이번 승인에 포함하지 않는다.

## 2. 입력과 데이터 경계

1. 업체 선택 → 접근 가능한 연결 상품 선택 → 목표 키워드 자동 채움/수정.
2. 업체·상품 ID의 명시적 연결만 사용한다. 판매처 이름이 비슷하다는 이유로 다른 상품 정보를 채우지 않는다.
3. 보유 자료의 현재 상품명·브랜드·카테고리·확인된 속성을 채운다. 현재 태그·타이틀·메타가 없으면 `미확인`으로 표시하며 직원 입력을 받는다.
4. 연결 상품이 없으면 상품 URL과 상품명 등 사실정보를 직접 입력할 수 있다. URL만 입력했다고 상세 수집이나 외부 API를 자동 호출하지 않는다.
5. 기존 업체 미선택 키워드 생성도 남긴다. 사실이 부족하면 일반 추천의 한계를 표시하고 원산지·중량·인증·효능을 창작하지 않는다.
6. 업체·상품·키워드·사실정보가 바뀌면 이전 결과를 무효화한다. 늦게 도착한 응답과 이전 업체의 이력을 새 업체 아래 표시하거나 저장하지 않는다.

## 3. 상위 20개 근거 모듈

- SEO 전용 캐시 읽기 모듈을 둔다. 읽기 전용 SQLite 연결을 사용하며 캐시 미스 때 큐 등록이나 외부 검색 호출을 하지 않는다.
- 상품 ID/URL 기준 중복을 제거하고 관측된 순위 1~20을 확인한다. 광고·그룹상품·카탈로그 처리 근거가 부족하면 검증 완료로 표시하지 않는다.
- 근거에는 확보 상품 목록, 관측 순위, 상품 ID/URL, 판매처, 카테고리, 가격, 수집 날짜/시각과 확인 가능한 출처 정보를 남긴다.
- 기존 저장에 없는 정확한 시각·검색 화면·광고 제외 여부는 `미확인`이다. 날짜만 있으면 날짜로만 표시한다.
- 상태는 `검증된 20개`, `부분 자료 N/20`, `오래된 자료`, `출처 미확인`, `자료 없음/읽기 실패`를 구분한다. 읽기 실패를 0건으로 간주하지 않는다.
- 오늘·어제 자료는 최신 범주, 2일 전부터는 오래된 자료로 표시한다. 어떤 날짜를 사용했는지 항상 보여 준다.
- 공통어는 상품당 최대 한 번만 집계한다. 분모는 실제 사용한 상품 수이며 비율은 100%를 넘지 않는다.
- 경쟁상품의 실제 태그·페이지 제목·메타 설명은 현 캐시에 없다. 상품명에서 유추한 값을 경쟁상품의 실제 설정값으로 표시하지 않는다.
- 근거가 부족해도 상품 사실에 기반한 기본 추천은 가능하다. 이때 `상위 20개 분석 완료`라는 표현은 금지한다.

## 4. 생성·오류 처리 모듈

- 사내 기준, 입력 상품 사실, 현 값, 캐시 근거를 구분하여 전달한다. 외부 상품명·직원 입력·사내 편집 내용은 자료이며 실행 지시가 아니다.
- 결과는 기존 `product_names/tags/category/rationale`를 유지하면서 페이지 타이틀·메타 설명과 항목별 변경 이유·근거 참조를 추가한다.
- 이름·태그·근거의 자료형, 배열 길이, 빈값, 필드 길이를 검증한다. 잘못된 JSON이나 문자 하나씩 쪼개진 목록을 정상 결과로 처리하지 않는다.
- 인증 실패, 크레딧/사용 한도, 모델 사용 불가, 공급자 장애, 시간 초과, 연결 실패, 응답 해석 실패를 안전한 코드와 직원 안내로 구분한다.
- 공급자 오류 원문·API키·상품/업체 정보·생성 원문을 공개 실행 로그에 남기지 않는다. 진단에는 분류·상태코드·시각·요청 식별자만 사용한다.
- 실패 시 유료 자동 재시도나 임의 모델 변경을 추가하지 않는다.
- 생성 성공 여부는 HTTP 상태만이 아니라 업무 결과와 출력 검증으로 판단한다.

## 5. 직원 검수와 저장

- 네 항목별 `현재값 → 추천안 → 변경 이유 → 채택/수정/보류`를 보여 준다.
- 후보 선택·직접 수정이 가능하며 채택되지 않은 항목은 현재값을 유지한다. 미확인 현재값은 그대로 미확인으로 보존한다.
- 최종 저장은 `승인본 저장`, 복사는 `승인본 복사`로 명명한다. 네이버 반영 완료라고 표시하지 않는다.
- 추천 원본과 직원 최종 승인본을 분리하여 업체·상품·키워드·입력 사실·근거 스냅샷·기준 버전·검토자·검토 시각을 기록한다.
- 기존 `client_seo_results` 저장·조회 계약과 과거 이력은 유지한다. 새 검수 정보는 가산 필드/별도 표로 보존하며 옛 줄을 일괄 수정하거나 삭제하지 않는다.
- 승인 확인 없이 생성 기록을 승인 완료로 저장하지 않는다. 같은 요청의 중복 클릭도 중복 승인본을 남기지 않도록 한다.
- CSV에는 네 항목·변경 이유·검토 상태·자료 시점·기준 버전을 포함한다. 스프레드시트 수식 삽입을 방지한다.

## 6. 사내 기준 개정 내용

1. 네이버 공식 정책, 실제 관측 자료, 회사의 검증 전 가설을 분리한다.
2. 상품명보다 먼저 상품 사실·카테고리·브랜드·속성을 확인한다. 실제 상품과 다른 옵션·원산지·인증을 창작하지 않는다.
3. 주요 관련 키워드 중심으로 명확하게 쓰고, 중복·무관 키워드·경쟁 브랜드·검증되지 않은 최상급 표현을 제외한다.
4. 브랜드·수량·원산지를 항상 특정 위치에 넣는 고정 공식은 폐지한다. 상품 정보와 읽기 쉬운 문장에 맞춰 판단한다.
5. 태그는 필요한 관련어만 최대 10개로 제안한다. 허용/제한 태그 사전 검증을 하지 못했으면 검증 완료로 표시하지 않는다.
6. 페이지 타이틀·메타 설명은 상품명과 별도로 고유하고 사실적으로 작성한다. API 한도와 노출 권장 길이·순위 효과를 혼동하지 않는다.
7. 상위 상품의 빈도가 높아도 해당 상품과 무관하면 채택하지 않는다. 공통어는 추천 근거 중 하나이지 순위 인과관계가 아니다.
8. 검색량·순위·매출 자료가 없으면 수치를 창작하지 않는다. 100/200위 기준이나 '자연판매 가능'을 확정 규칙으로 쓰지 않는다.
9. 직원 검수 후 승인본을 기록하고 직원이 스마트스토어에서 수동 반영한다. 순위·매출 상승을 보장하지 않는다.
10. 변경 전후와 실제 측정 자료를 구분하여 후속 점검한다. 복사·저장을 외부 반영 완료로 간주하지 않는다.

기존 규칙 원문과 해시를 이력에 보관한다. 개정본은 명시적인 관리자 전환으로 활성화하며, 부팅만으로 운영 DB의 사용자 편집 내용을 덮어쓰지 않는다. 구 기준이 활성 상태이면 화면에 구 기준 사용을 표시한다.

## 7. 운영 읽기 전용 진단

- 기존 저장소에 정상 설정된 GitHub Actions SSH 인증 경로를 사용한다. 별도 서비스에서 자격증명을 꺼내 쓰지 않는다.
- 기존 진단 워크플로의 SEO 전용 분기를 두고, 이 모드에서는 다른 기본 진단·적용 작업을 건너뛴다.
- 컨테이너 기동 시각·이미지 식별자·SEO 소스 해시, 키 설정 유무, 모델명만 확인한다.
- Docker의 시각 포함 로그를 읽어 공급자 응답 수신·호출 오류·JSON 해석 실패·컨텍스트 수집 생략을 각각 집계하고, 확인 가능한 최초/최종 시각·안전한 오류 분류를 출력한다.
- 현재 응답 수신 로그는 JSON 검증 전 기록이며 요청 식별자가 없다. 과거 업무 생성 성공 건수는 확정하지 않고 `미확인`으로 표시한다. 로그가 없는 키 미설정·시간 초과도 과거 발생 건수를 추측하지 않는다.
- 로그 보존 시작 시각·회전 범위를 함께 확인한다. 보존 로그의 첫 오류를 실제 장애 시작일로 단정하지 않는다.
- 저장된 생성 결과 수·최초/최종 저장 시각은 별도 참고 지표이며 마지막 생성 성공과 같다고 단정하지 않는다.
- DB는 읽기 전용·쿼리 전용으로 연다. 앱 모듈을 import하여 초기화·스케줄·DB 쓰기를 유발하지 않는다.
- 공급자 추가 호출, 네이버 추가 수집, 설정 변경·재기동·배포·운영 데이터 수정은 하지 않는다.

## 8. 호환성과 시험

- 기존 생성·저장·조회·규칙 편집 요청과 응답을 가산 방식으로 유지한다.
- 공용 `POST /api/seo/analyze`, 스토어·플레이스 분석, 업체 피커·SSO·전산 소비 API는 변경하지 않는다.
- 가짜 SQLite와 공급자 모형으로 테스트하며 실제 업체 저장을 사용하지 않는다.
- 필수 회귀: 기존 저장 이력, manager/superadmin 권한, 다른 업체 접근 거부, 업체 전환과 응답 역전, 상품 ID 오연결 방지.
- 자료 회귀: 0/부분/20개/중복/광고미확인/오래됨/DB읽기실패, 상품당 빈도, 누락값 비창작, 캐시 미스 때 네트워크·큐 쓰기 0건.
- 생성 회귀: 4항목 정상 출력, 잘못된 JSON/자료형/길이, 공급자별 오류·응답 부족·시간 초과, 민감정보 미출력.
- 저장 회귀: 원본과 승인본 구분, 수정·보류 보존, 중복 클릭, 승인자·기준·근거 보존, 옛 행 무변경, CSV 안전성.
- 로컬 브라우저에서 업체→상품→생성→수정→승인 저장→새로고침→복사를 가짜 자료로 검증한다.
- 운영 생성 복구는 실제 원인 조치와 승인된 배포 후 최초 실패 입력으로 다시 확인해야 한다. 로컬 시험만으로 운영 복구 완료라고 말하지 않는다.
