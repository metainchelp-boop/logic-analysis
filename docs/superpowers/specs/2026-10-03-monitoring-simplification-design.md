# 관제 단순화 — 사용자 승인 반영 설계·검증 계획

## 승인 근거와 범위

2026-10-03 자체 제한 32개 제안에 대한 대표의 수정 지시와 “언급한 내용과 권장하는 부분 접목해서 개선 작업”을 반영한다. 로컬 구현·검증 범위이며 이번 지시로 배포/광고 변경/운영 데이터 일괄 변경을 실행하지 않는다. 새 기획 재승인을 반복하지 않고 확정한 업무 목적을 검수 기준으로 삼는다.

## 목적

관제는 업무 결재·계약 수정 도구가 아니라 이관 계정의 현황·성과·이상 감지를 보는 곳이다. 광고 설정을 변경하는 자동화는 별도 후속 설계다.

1. 현재 이관된 네이버 계정은 전부 목록에 남긴다. 실관리 4단계(진행중·사후관리·전략관리·재계약진행중)는 전일 매일 수집, 그 외는 주 1회 일요일 시작한다. 미완료는 이어서 수집한다.
2. 계약 종료일+14일/구형 허용7단계는 계정 식별·연결확정 조건으로 사용하지 않는다. 실제 광고 쓰기 권한을 풀지 않는다.
3. 전산 연결됨, 전산 업체 확인 필요(후보/번호충돌), 전산 미등록·비관리 계정을 구분한다. 후보는 등록이 없다는 확정 증거가 아니므로 미등록으로 단정하지 않는다. 이 회사 귀속 판정과 계정 단위 읽기 수집을 분리한다.
4. 현재 이관 권한과 원천 완결성은 검증한다. 불명확한 업체로 실적을 귀속하거나 직원에게 타 업체 자료를 보여주지 않는다. 대표는 전체, 팀장 포함 일반 관리직원은 본인 메인/서브만 본다.
5. 확정 연결·일별 실적은 유지한다. 목록 갱신은 새 계정/이관해제/담당/번호변경 탐지이며 매번 직원에게 다시 연결하라고 하지 않는다. 업무단계 변경은 앞으로의 수집주기만 바꾼다. 이전 자료 삭제 없음.
6. 전일 수집은 자동이다. 직원 수동 수집·관리 포함/제외·보고서 승인/보류 버튼을 모니터링 화면의 주 동선에서 제외한다. 대표 복구 도구는 접힌 보조 기능으로 보존한다. 전산 계정번호 보완 링크는 유지한다.
7. 수집은 진행분을 저장하고 이어 읽는다. 회차 종료30초 공백·내부예산2분 대기 등 불필요한 대기를 완화하되 외부 속도제한/인증거절·데이터 정확성 보호는 유지한다. 상세 구조·성과가 서로 굶지 않도록 예산을 배분한다.
8. 보고서는 현재 실관리 업체만 자동 생성·목록 표시한다. 종료/비관리 업체의 이전 보고서·실적을 삭제하지 않는다. 현재 실관리 업체의 정정 이력과 과거 귀속 검증은 유지한다.
9. SSO는 referrer 부재만으로 막지 않고, 정확한 opener/source/origin/requestId/PKCE 검증을 유지한다. iframe/알 수 없는 출처 차단 유지. 무활동1시간→4시간, 서버세션12시간 유지. 갱신 재시도가 토큰만료를 넘지 않게 한다.
10. 저장은 계정·날짜별 숫자와 필요한 상태/변경 기록 중심이며 화면/광고 원문 전체를 계속 복제하지 않는다. 자료를 삭제하거나 백업을 없애지 않는다. 백업은 아침점검 완료와 분리하여 일일 복구사본을 보장한다. 용량은 합성자료와 실제운영을 구분해서 보고한다.

## 대안 판단

- 모든 가드를 해제: 간단해 보이나 오귀속·정보유출·호출폭주·잘못된 정상판정 위험으로 제외.
- 기존 제한에 수동 버튼 추가: 직원 업무를 늘리고 사용자 모니터링 목적에 맞지 않아 제외.
- 선택한 안: 계정 목록/업체 귀속/수집/보고서를 분리하고 정상 흐름을 자동화. 기존 보안·정합성 경계는 보존.

## 검증 순서

1. 연결/수집정책: 종료일 오래됨·환불완료·숨김/미상·미등록·후보·충돌·이관해제 사례. 일일/주간 분기, 미확정 실적 오귀속 없음.
2. 수집: 합성 HTTP/시계로 고정 공백 제거, reader 간 속도계, 429 대기, 진척 이어읽기, 자동 복구, 아침점검 범위 검증. 1,792계정 합성 결과는 운영 완료시간 보증이 아님.
3. 보고서: 일일→주간 전환 시 신규 보고서 생성/기본목록 제외, 과거 실적/판 보존, 다시 실관리로 전환 시 이용 가능. 후보·전산미등록은 업체 보고서 없음.
4. 접속/UI: referrer 없음+정상 전산 메시지 허용, 잘못된 출처/창/코드 거절,4시간 무활동/12시간절대기한, 갱신복구, 직원 본인범위.
5. 백업: 아침점검이 없어도 로컬사본/암호화전송, 재시도/하루중복방지/복원 무결성 회귀.
6. 전체 관련 테스트·정적검사·실제 브라우저 합성 화면을 확인한다. 운영 배포·직원PC실증·운영10시간내완료는 별도 검증 단계로 명시한다.

## 외부 제한 근거

네이버 공식 FAQ(2026-10-03 확인)는 총 호출량 상한 없음, Customer ID별 실시간 속도 제한,429 후 재시도를 설명한다. 고정 초당3회는 공식 한도가 아니라 현재 제품 내부 안전 예산이다. https://github.com/naver/searchad-apidoc/wiki/FAQ

한 번의 조회실패는 ID 불명과 다른 축이다. 업체 연결 오류, 내부 처리시간 부족, 네이버 응답/집계 지연, 접근권한 오류를 구분해서 표시·재시도한다.

## 검증에서 확인한 반복 중단 보완 — 2026-10-04

활동 캠페인 29개는 상세 점검에 최소 32번의 조회가 필요한데 구형 경로는 회차 24번에서 중단된 내용을 저장하지 않았다. 3회 연속 같은 지점에서 멈추는 합성 재현을 확인했다. 위 7번의 진행 저장과 전체 계정 관찰 요구를 충족하기 위해 이번 로컬 구현에 상세 점검 책갈피를 포함한다.

- 캠페인 합계 100개 묶음과 일별 자료를 완료 단위로 저장하고 다음 회차/프로세스 재시작에서 이어 읽는다.
- 현재 이관·귀속·날짜와 실제 판정 필드가 유지될 때만 재사용한다. 동일 내용의 수신시각 갱신만으로 진척을 버리지 않는다. 최종 목록 재검사까지 끝나기 전에는 정상 판정/이슈 해소를 하지 않는다.
- 계정별 현재 헤더와 재사용 슬롯으로 행 누적을 제한한다. 오래된 광고 실적을 삭제하지 않고 새 임시 진행자료도 날짜마다 무한 복제하지 않는다.
- 실제 인증·호출 제한·통신 오류, 손상, 자료 지연, 최종 확인 직전 예산 소진, 원장 기록 실패와 재시작을 회귀 검증한다.
- 단순 설정 상한 해제나 네이버 병렬 요청 확대는 하지 않는다. 큰 구조의 10,000개 보호선 자체를 무제한 해제하는 변경과는 별개다.
