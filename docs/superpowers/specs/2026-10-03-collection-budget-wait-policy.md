# 내부 한도 대기와 실제 실패 횟수 분리

대표의 「응 그렇게해」로 후속 정책 확정. 순차 개선 1번의 개발 후보이며 **이 문서 작성은 운영 배포 승인이 아니다.** 앞선 조사·검증은 [수집 지연 후속](2026-10-03-collection-deadline-followup.md)에 보존한다.

## 확정 동작

- 실제 실행 중인 성과·구조 수집에서 `REQUEST_DEADLINE`·`REQUEST_CALL_CAP`만 실패 횟수 증가에서 제외한다. 대기 상태와 기존 다음 조회 시각 계산은 유지한다.
- 기존 실제 실패가 있으면 그 횟수를 지우지 않는다. 예: 통신 실패3회 → 내부 한도 대기 → 통신 실패1회 = 4회로 중단. 기존2/5/15분 재시도 간격을 줄이지 않는다.
- 같은 요청에 선행 통신 오류가 있으면 `SERVER`·`NETWORK`·`RATE`를 기록하여 면제 대상에 넣지 않는다. 구조 경로에서도 성과와 같은 원인 보존을 적용한다. 4회 중단 후 마지막 실제 원인도 보존한다.
- 옛 `REQUEST_BUDGET`은 상세 원인이 모호하므로 면제하지 않는다. 기존 중단 작업을 다시 여는 마이그레이션이나 초기화는 없다. 기존10건의 원인을 소급 추정하지 않는다.
- 요청당/회차/초당 호출 한도, 대기, 429 중단, 현재 권한과 원천 검증, 진척 시 기존 실패 예산 초기화, 성공값과 체크포인트 보존은 유지한다. 스키마 변경 없음.
- 비활성 옛 전체목록/월간 수집기, 별도8회 제한의 지표 송신은 변경하지 않는다.

## 검증 기준

실제 Store와 메모리 SQLite·합성 HTTP·가상 시계를 사용하고 외부 소켓은 차단한다.

1. 순수 내부 한도6회에도 계속 대기하며 다음 시각 전 요청은 거부한다.
2. 실제 오류3회 사이의 내부 대기는 누적값/간격을 초기화하지 않고 4번째 실제 오류에서 중단한다.
3. 실제 수집기에서 순수 한도와 선행 통신 오류가 있는 한도를 구분한다. 429 대기와 호출량 제한을 유지한다.
4. 구버전 모호한 오류와 이미 중단된 작업은 자동 해제하지 않는다.
5. 기존 성공 금액·확인 시각을 보존한다. 601캠페인 중600개 완료 뒤 반복 한도 대기를 거쳐 나머지1개만 수집하고 정확한 합계로 완료한다.

로컬 관련76시험 통과(서로 겹치는 중간 실행은 합산하지 않음). 신규 성과7·구조6시험을 포함하며, 내부 한도6회 대기/실제 오류4회 중단·원인 보존을 실제 Store 공개 경로로 확인했다. 초기 통합 명령에서 잘못된 시험 모듈명2개로 가져오기 오류가 있었으며 실제 경로로 정정한 전체76시험이 통과했다. Linux 전체 CI 결과는 완료 후 기록한다. 로컬 메모리 시험은 운영 실계정·파일 DB 검증을 뜻하지 않는다.
