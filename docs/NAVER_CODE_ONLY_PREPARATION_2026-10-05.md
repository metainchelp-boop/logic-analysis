# 관제 코드 전용 배포 준비 · 2026-10-05

## 승인과 현재 결과

- 대표의 「그렇게해」는 운영 DB를 보존하는 코드 전용 배포 절차 준비·검증 승인이다.
- `backend/tools/naver_preview_code_only.py`를 추가했다. 기존 배포기와 워크플로는 변경하지 않았다.
- 실제 운영에 적용한 수정본은 없다. 수집기 종료 원인은 미확정이며 제품 수정본도 아직 없다.
- 이번 검증은 로컬 가짜 서비스 어댑터를 통한 배포 순서·실패 처리 시험이다.
  운영 DB 열기·제품 배포·서비스 재시작·운영 데이터 복원/삭제·네이버 호출은 하지 않았다.
- 앞선 제품 종료 재현 작업은 실행 도구의 안전 제한으로 거절되었다. 이를 다시 실행하거나 다른 수단으로 우회하지 않았다.

## 승인한 설계와 구현

기존 배포 모듈을 직접 변경하는 방법과 별도 코드 전용 경로를 비교했다.
기존 모듈에 최소 분기를 추가해도 준비 패키지의 고정 크기 제한을 초과했다.
따라서 기존 운영 경로·전송 제한은 그대로 두고, 새 경로에서 검증된 공통 헬퍼만 재사용했다.

1. **시작 전** — 검토된 구판/신판 커밋, 두 압축물 해시, 두 Store 해시, 호스트 기준선이 모두 일치해야 한다.
   입력값으로 검토 승인을 만들 수 없다. 현재 `REVIEWED_TRANSITION=None`이므로 호스트 접근 전에 거절한다.
2. **준비** — 기존 패키지·봉인·이미지·파일 권한·변경 경로·schema SQL/이관 함수 검사를 유지한다.
   설정 시험은 기존의 별도 프로젝트·차단망 `check-config`를 사용한다. 이 명령의 현재 소스는 DB를 열지 않는다.
3. **교체** — 전용 relay→engine 정지 및 PID/이미지/소스 확인 후 코드 컨테이너와 unit만 교체한다.
   DB snapshot·사전 원천 동기화·직접 schema 조회는 호출하지 않는다.
4. **확인** — 메모리 상태 응답, 정적 자산, 비로그인 401/403, 서비스·컨테이너 메타데이터만 확인한다.
   수집 완료나 DB 무결성 확인을 주장하지 않는다.
5. **실패** — 양쪽 정지를 확인하고 호스트·bootstrap·소스 호환성·기존 배포 기록을 다시 검사한다.
   확인된 구판 코드와 unit만 되돌린다. DB/DB-WAL/DB-SHM/DB-journal을 복사·교체·이동·삭제·복원하지 않는다.
   정지나 호환성 또는 코드 복원에 실패하면 재시작을 진행하지 않고 양쪽 중지를 시도하며 실패로 보고한다.
   중지 명령 자체가 실패할 수 있으므로 이 결과를 실제 중지 완료로 단정하지 않는다.

**DB 보존의 의미:** 배포기가 운영 데이터 파일을 조작하지 않는다는 뜻이다.
서비스 종료·재개 과정의 정상 DB 처리 및 기존 스케줄러 쓰기까지 없다는 뜻은 아니다.
코드를 되돌렸다는 결과도 수집기 장애 해결이나 수집 정상 완료의 증거는 아니다.

## 검증 근거

- 새 경로 11개 테스트: 미검토 거절, 성공 시 DB 헬퍼 호출 0, 무접속 준비,
  부분 교체 실패의 코드 복원, 정지/복원 실패 처리, schema·인프라·범위 오류 사전 거절,
  각 검토 pin 불일치, bootstrap/호스트/소스 변경 시 구판 재시작 차단, 오류 원문 비노출, 워크플로 비활성.
- 기존 DB 헬퍼 호출을 감시하고 신규 준비·코드 복원 시험에서 SQLite 연결을 금지했다.
  테스트는 기존 합성 파일·가짜 명령 어댑터를 이용하며 운영 DB를 쓰지 않는다.
- 전체 `python3 -m unittest discover -s backend/tests -p 'test_naver_preview*.py'`: **280개 통과**.
- 독립 검토에서도 280개 및 `git diff --check` 통과, 추가 차단급 문제 없음.
- 기존 배포 모듈·워크플로·제품 봉인 pin 변경 0. 준비 패키지 131072바이트/전송 65536바이트 제한 유지.

## 운영 활성화 전 남은 조건

- 차단된 원인 검증의 제한을 정식으로 해결하고, 종료 원인에 맞는 제품 수정본·회귀 증거를 확보해야 한다.
- 현재 운영 상태를 다시 확인해야 한다. 기존 `current_state`는 활성 서비스를 요구하므로,
  서비스가 멈췄다는 이유로 해당 검사를 약화하거나 건너뛰어서는 안 된다.
- 구판/신판의 schema뿐 아니라 새 코드가 기록한 데이터도 구판이 해석할 수 있는지 검토해야 한다.
  데이터 형식 변경이 필요한 제품 수정은 이 코드 전용 경로의 승인으로 처리하지 않는다.
- 검증된 실제 전환의 소스/압축물/Store 해시·변경 경로·정적 자산 계약을 갱신하고 검토 tuple을 고정해야 한다.
  과거 0a30285→a38c537 전환을 그대로 재사용하지 않는다.
- 새 모듈의 준비/적용/고정 오류 보고를 워크플로의 명시적 경로에 연결하고 전송 왕복·한도 시험을 다시 통과해야 한다.
  현재 워크플로에는 연결하지 않았으므로 운영에서 선택·실행할 수 없다.
- 실제 적용 후 별도로 비접속 진단, 수집 연속성, 사용자 화면을 검증해야 한다.
  현재 중단된 운영 직접 DB reader를 편의상 다시 사용하지 않는다.
