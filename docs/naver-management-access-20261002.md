# 관제 접근 정책 변경과 검증 범위

## 현재 정책

- 재직 대표(`is_top_manager`)만 전체 계정과 광고주를 봅니다.
- 관리팀 여부는 전산의 `employee.authority.departmentType == MANAGEMENT`에서 만든 `employees[].is_management`만 사용합니다. 이름·팀명·`is_manager`를 관리팀의 근거로 쓰지 않습니다.
- 직원의 재직 조건은 `status == ACTIVE`이면서 `is_deleted == false`입니다. 관리팀 직원과 팀장 모두 본인의 메인·서브·직전 담당 범위만 봅니다. 기존 직전 담당의 보기·멈추기 제한은 유지합니다.
- `is_management`가 없거나 정확한 불리언 `true`가 아니면 관리팀 접근을 허용하지 않습니다. 대표의 전체 범위는 유지합니다.
- 대표의 직원 고르기 명단은 재직 관리팀만, 직원에게 내려가는 명단은 본인만입니다. 팀 목록은 빈 배열입니다. `person:<직원>` 선택은 그 직원의 실제 메인·서브·직전 담당 합집합으로 계산합니다.
- 팀 계층 조회, 다른 직원 담당에 대한 팀장 승인·알림·묶음정지는 폐지합니다. 담당자에게 갈 수 없는 일은 대표로 이어지며, 알림 수신자·승인자는 현재 열람 가능한 사람의 부분집합이어야 합니다.

## 배포 선행 조건

전산 백엔드가 조직 스냅숏에 `is_management`를 추가하고 실제 수락본이 갱신되는 것이 선행 조건입니다. 관제 코드를 먼저 배포하면 필드가 없는 저장 스냅숏에서 관리팀 직원도 차단됩니다. 기존 데이터에 추측한 관리팀 값을 채워 넣지 않습니다. 배포·재시작·운영 DB 수정은 이 작업에서 하지 않았습니다.

`naver_engine/fields.py`의 조직 직원 허용 필드에도 `is_management`를 추가하여, 수락본 저장 때 권한 근거가 유실되지 않도록 했습니다. 토큰에는 여전히 직원 번호와 시각만 남기며, 요청마다 현재 수락 조직으로 범위를 다시 계산합니다. 직원의 낡은 조직 조회 차단은 `web._viewer`가 담당합니다.

## 과거 알림

현재 알림 저장 형식에는 광고주별 번호 없이 과거 집계 숫자만 남습니다. 그러므로 직원에게는 일반 안내와 관제 홈 경로만 주며, 예전 숫자와 원래 경로를 돌려주지 않습니다. 시스템·전사·옛 팀장 집계와 모르는 문구 틀은 대표만 봅니다. 새 알림 스키마나 발송 활성화는 추가하지 않았습니다. 기본 비활성 발송 설정은 유지합니다.

## 시험 변경의 의미

이전 `TEAM` 허용 시험을 건너뛰거나 삭제하여 통과시킨 것이 아닙니다. 팀장에게 팀원 조회·승인·알림을 허용하던 기대치를 명시적으로 `MINE`·거절·대표 이관으로 바꾸었습니다. 범위 밖과 없는 번호가 같은 응답인 시험, 위조·옛 Scope 거절, 대표 번호 0, 메인·서브·직전 담당, 퇴사·정지·삭제, 묶음 확인 원자성, 알림·승인 부분집합 불변식은 계속 실행합니다.

새 정책의 대표/관리팀/비관리팀 구분, 필드 누락·오류 차단, 직원 명단 제한, 팀 선택 거절, 서브를 포함한 직원 선택, 과거 알림 숫자 가림은 각각 실패를 확인한 뒤 구현했습니다. 관리팀 권한 회수와 담당 이관도 현재 스냅숏으로 재검증합니다.

## 로컬 검증의 한계

순수 조직·권한 시험은 실제 로컬 Python으로 실행했습니다. SQLite를 쓰는 웹·알림 기능 시험은 macOS에서 원래 파일 잠금과 SQLite 잠금이 충돌하여 신규 임시 DB부터 `database is locked`로 실패했습니다. 상위 작업의 승인에 따라 시험 프로세스 안에서만 `fcntl.flock`을 임시 무동작 함수로 대체해 기능을 검증했습니다. 이 대체는 소스·시험 파일에 저장하지 않았으며 실제 파일 잠금·동시쓰기 안전성 검증으로 보지 않습니다. Linux CI의 원래 잠금 구현을 사용한 전체 시험이 별도로 필요합니다.
