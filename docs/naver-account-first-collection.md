# 계정우선 원천 수집의 실행 계약

## 범위와 기본 상태

`NAVER_ENGINE_INVENTORY_ENABLED`는 기본 `false`입니다. 코드 추가는 운영 활성화·배포를 뜻하지 않습니다.
켜진 경우 최신 수락된 네이버 이관 목록의 `present=1` 계정을 전산 매칭·계약 종료일과 무관하게 읽습니다.
매칭과 계약 단계가 필요한 기존 `morning`·`metrics` 경로는 유지합니다. 원천 수집 결과를 ERP에 자동 귀속하거나 전송하지 않습니다.

최신 목록 동기화가 실패/보류됐거나 수락 목록이 30시간을 넘으면 요청하지 않습니다. 각 HTTP 요청 직전에 목록 시각과 계정의 현재 위임을 재검증합니다.
읽는 항목은 캠페인 목록, 비즈머니, 전일 캠페인 성과 합계입니다. 통계의 일부 행·값·기준 시각이 빠졌으면 모름으로 남기며 0으로 바꾸지 않습니다.

## 요청 제한과 이어서 처리

- 한 회차 최대 3개 계정, 실제 HTTP 최대 24회, 회차 30초, 계정별 최대 8회·10초입니다.
- 기존 초당 3회 제한과 GET·호스트·경로 허용 목록을 유지합니다. 재시도와 통계 100개 단위 분할 요청도 HTTP 예산을 사용합니다.
- 외부 전송 timeout은 남은 시간으로 줄이고 긴 429 대기는 회차를 중단합니다. 진행 중 네트워크가 전송 구현의 timeout을 무시하는 경우 강제 종료를 보장하지는 않습니다.
- 계정×한국 날짜의 시도·상태를 먼저 저장하므로 프로세스 재시작 뒤 같은 계정만 반복하지 않습니다. 미시도 계정 우선, 이후 오래 기다린 재시도 순입니다.
- 실패 재시도 대기는 2/5/15/30분이며 같은 원천에서 연속 실패는 최대 4회입니다. 검증된 새 배치가 진행되면 연속 실패 수는 초기화합니다. 진행 회차 자체는 실패 예산을 소모하지 않습니다.
- 최대 100개 캠페인씩 전일 합계를 읽고 검증된 배치마다 목록 지문·다음 위치·배치 정수 합계를 원자적으로 저장합니다. 다음 회차/프로세스 재시작에서는 확인된 배치를 다시 합산하지 않습니다.
- 매 회차 캠페인 번호 목록을 다시 읽습니다. 목록이 바뀌면 이전 부분합을 버리고 현재 목록으로 다시 시작합니다. 마지막 배치 뒤에도 목록을 재검증하고 완결된 경우에만 전일 지표를 공개합니다.
- 부분 원천의 SHA-256 지문·배치 수·배치 경계·계정·날짜·정수 합계가 맞지 않으면 `limited/CHECKPOINT_INVALID`로 중단합니다. 권한/인증 거절은 `reauth_required`, 연속 4회 실패 소진은 `limited/RETRY_EXHAUSTED`이며 같은 날 자동 반복하지 않습니다.

## 화면 상태

| 상태 | 뜻 |
| --- | --- |
| `pending` | 오늘 아직 시도하지 않음(저장 행 없음) |
| `reading` | 시도를 기록하고 읽는 중 또는 도중 중단 후 재시도 대기 |
| `partial` | 검증된 일부 배치를 저장하고 다음 회차에 이어 읽기 |
| `ok` | 이번 계정의 캠페인·잔액·전일 지표를 완결 확인 |
| `retry` | 일시 실패·자료 미완결·회차 예산 때문에 대기 |
| `reauth_required` | 네이버 권한/인증 거절, 운영자 확인 필요 |
| `limited` | 부분 원천 검증 실패 또는 연속 4회 재시도 소진 |

전일 지표가 없으면 `NULL`입니다. `ok`는 기존 업무 규칙의 정상 판정이나 광고 성과를 뜻하지 않습니다.
계정 원천 저장소는 기존 계정 일별 점검·캠페인 일별 기록·이슈·매칭 판단·ERP 성과 스냅샷과 별도입니다.

## 처리량 추정과 검증 한계

현재 실행 루프는 한 회차 뒤 60초를 기다립니다. 첫 시도 전체 처리량은 대략 `ceil(계정 수 / 3) × (60초 + 실제 회차 시간)`입니다.
예를 들어 **1,798개라는 가정**에서는 600회차로 최소 약 10시간에 실제 읽기 시간이 추가됩니다. 매번 30초를 사용하면 약 15시간입니다.
이는 운영 계정 수·실제 완료시간을 측정한 값이 아닙니다. 다른 예약 작업·실패·재시도·목록 갱신 시간이 더해질 수 있습니다.
601개 캠페인 계정은 기본 예산에서 첫 회차 600개까지 저장하고 다음 회차에 나머지와 최종 목록을 확인하는 예시 테스트를 통과했습니다. 큰 계정의 추가 회차는 위 첫 시도 처리량 추정에 포함되지 않습니다.
신규 계정은 회차 시점 최신 목록에서 선택하며 날짜가 바뀌면 새 일별 결과를 만듭니다. 모든 계정의 `ok` 여부와 제한/권한거절 개수를 별도로 확인해야 합니다.

로컬 macOS 기능 시험은 임시 DB에서 `flock`만 대체한 명시적 하네스를 사용합니다. 운영 잠금 코드는 변경하지 않습니다.
이 결과는 실제 Linux 파일 잠금·운영 네이버 응답·운영 전체 처리량 검증과 구분합니다.
